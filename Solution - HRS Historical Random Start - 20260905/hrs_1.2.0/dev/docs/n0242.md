# HRS 1.2.0 arrival-biome protection and zone-trader manifest

Date: 2026-09-01
Status: implementation and live QA planned; no pass claim yet
Scope: `Starting biome only` protection plus one-time same-biome opening trader, one fresh game per biome

Historical route: read `n0243.md` for the chronological development story,
including the framework behaviors that produced the Snow, trader, and primed
landing methods reused here.

## Objective

Prove two coupled outcomes from one confirmed Random landing:

1. A player who deliberately enables `Starting biome only` receives protection
   from the dangerous-biome hazard family at the confirmed initial landing,
   without disabling unrelated biome hazards, enemies, ordinary damage,
   weather presentation, progression, or later biome behavior.
2. The native opening trader quest is adjusted once to the nearest valid trader
   inside that same initial biome/zone, so the first progression trip does not
   require crossing another biome merely to reach its trader.

The initial settled biome is immutable authority for both decisions. Protection
and trader routing do not follow later travel: entering another dangerous biome
must expose the player to that biome's normal hazard, and the already-routed
opening quest must continue pointing to the original same-zone trader.

This is a biome-behavior cycle, not another geometry survey. Every selected
location already passed the controlled 171/171 landing certification.

## Proven predecessor and reuse decision

This cycle extends two existing working solutions; it does not replace them
with a new architecture.

### Snow arrival protection precedent

The earlier NG01 Snow implementation established the narrow per-character
pattern that 1.2.0 will generalize:

- signed exact-game `RandomSafe` policy;
- completed one-shot relocation marker as the eligibility gate;
- persisted `bitwrecked_hrs_biome_v1 = 8` Snow-family authority;
- removal of only `buffSnow_Hazard`, `_Over`, `_Recover`, `01`, and `02`;
- maintenance of `$SnowHazardTimer` at `$SnowHazardTimerMax`; and
- no vanilla XML or global `BiomeProgression` mutation.

The owner observed the Snow landing without the unwanted starting debuff. The
implementation and its intended isolation are routed through `n0231.md` and
the consolidated engineering record `n0233.md`. Those records also truthfully
state the evidence boundary: the immediate Snow behavior worked, while the
full-duration, reload, death, unrelated-save, and removal matrix was not
completed as a historical release proof. The 1.2.0 matrix closes that gap.

### Opening-trader precedent

`HRS_TRADER_006` is the working native-quest example. Its fresh `RandomSafe`
game completed this recorded path:

`NG01 -> RELOCATION_COMPLETED -> TRADER_ROUTE_RESERVED -> TRADER_ROUTE_SELECTED -> TRADER_ROUTE_COMPLETED`

The Journey to Settlement destination moved from the native Pine Forest route
at about 2.4 km to the nearest authored trader without fallback or exception.
The proof covered relocation, ordinary tutorial completion, the exact phase-one
`trader` objective, native `ObjectiveGoto.SetLocation`, journal refresh, and
one-time route completion. It is routed through `n0232.md`, `n0234.md`, and
`n0235.md`; the archived bridge policy/result additionally preserve the exact
game name and completed relocation transaction.

### What changes in 1.2.0

Retain the proven event timing, exact quest/objective match, native destination
write, refresh, marker gates, Snow cleanup, and bounded logging. Change only:

1. resolve and persist the actual grounded arrival biome for every promoted
   point, rather than inferring Snow from `NG01`;
2. map that biome to Burnt, Desert, Snow, Wasteland, or no protection for Pine;
3. filter legal traders to the persisted initial biome before applying the
   already-proven nearest-distance and native-objective update path; and
4. add explicit feature results and the missing persistence/isolation evidence.

The first implementation target remains Navezgane V3.2 (b9). Dynamic trader
discovery for player-generated random worlds is a later compatibility gate and
must not be claimed from the five Navezgane cases alone.

The installed Navezgane registry/catalog provides one reviewed opening trader
in each test biome:

| `TP01` | Trader Bob | `941, -1566` | `971, -1536` | Desert |

| `TP03` | Trader Jen | `190, -144` | `220, -114` | Burnt Forest |

| `TP05` | Trader Rekt | `428, 644` | `458, 674` | Pine Forest |

Selection order for an eligible completed Random relocation:

1. Resolve and persist the actual biome at the final grounded landing.
2. Query the current world's authoritative valid trader registry.
3. Determine each legal trader placement's actual biome in the loaded world.
4. Keep only traders in the persisted initial biome.
5. Select the nearest remaining trader by planar X/Z distance, with stable
   coordinate/identifier tie ordering.
6. Reserve and update only the phase-one `trader` objective of
   `quest_whiteRiverCitizen1`, verify the destination, and mark the route
   completed before allowing another callback.

This supersedes the inherited `closest valid trader across any biome` rule for
1.2.0. It remains relational to the relocated player, but the candidate set is
now constrained to the player's initial zone. If no valid same-zone trader can
be proven, fail closed and preserve the native objective; do not silently pick
a cross-biome trader, reset/re-add the quest, or reroll after reload.

The route is exactly once. Leaving the initial biome, dying, reloading,
reconnecting, or later accepting another quest must not select another trader.
The normal interaction, 500 XP, stone shovel, trader progression, inventory,
and later quests remain native.

## Current gap

The inherited runtime implements only Snow protection. It records a Snow
marker, removes the five Snow hazard buffs, and holds the Snow timer at its
maximum. Burnt Forest, Desert, and Wasteland do not yet have equivalent
runtime behavior.

The gap is therefore generalization and proof, not discovery of an entirely new
solution. The Snow and trader paths remain the regression oracles while each
additional biome family and the same-biome candidate filter are introduced.

## Persisted state and transaction boundaries

The implementation must distinguish these facts even if compact numeric CVars
are used underneath:

| Fact | Meaning |
| --- | --- |
| Relocation state | Existing Absent/Reserved/Completed one-shot authority |
| Initial biome | Immutable actual biome resolved at the final grounded landing |
| Protection family | None for Pine or exactly one of Burnt/Desert/Snow/Wasteland |
| Protection result | Not requested, not applicable, active, or failed closed |
| Trader route | Absent, Pending, Reserved, Completed, or terminal failed closed |
| Selected trader | Stable reviewed identity and destination used for readback |

`bitwrecked_hrs_biome_v1` historically stores the protection-family mask, not
a complete biome identity. Do not reinterpret its legacy Snow value `8` as a
new encoding. Add a separately namespaced initial-biome value or version the
state contract so Pine can retain trader-filter authority while correctly
having no dangerous-family protection bit.

A successful grounded relocation remains consumed even if an optional
protection or trader action fails. Feature failure must not leave relocation
Reserved and must never cause another relocation after reload. Conversely, the
relocation result alone must not be presented as protection or trader success.

For the trader transaction, Pending means the exact opening quest has not yet
been claimed. Reserved consumes the one routing attempt before mutation.
Completed requires destination readback. Any no-candidate, write, readback, or
marker failure becomes a terminal failed-closed/invalid state that preserves or
restores the native objective and prevents a reload reroll.

Existing 1.1.0 characters are compatibility inputs, not candidates for state
invention. A Completed old relocation must never run again; a Completed old
trader route must never reroute. A recognizable legacy Snow value may retain
only its already-authorized Snow behavior. If no persisted initial biome exists,
1.2.0 must not infer one later from wherever the player happens to be standing.

The inherited trader implementation removes the Pine Forest restriction and
selects the globally nearest valid trader. It does not yet restrict candidates
to the persisted initial biome. Therefore none of the five integrated cases
may be reported as a 1.2.0 pass until both generalized protection and same-zone
trader routing, including revised contracts, exist.

## Required implementation contract

1. After the primed landing is confirmed, resolve the actual arrival biome at
   the settled player position; do not trust only the requested catalog label.
2. Convert only a recognized dangerous arrival biome into one protection bit.
   Pine Forest produces no dangerous-family bit.
3. Persist the selected family for the exact eligible character and Random
   transaction. Standard remains an exact no-op.
4. Remove only that family's root, `_Over`, `_Recover`, `01`, and `02` buffs.
5. Hold only that family's timer at its native maximum while protection is in
   scope. Do not zero or rewrite the other three families.
6. Reapply the invariant safely after load without repeating relocation or
   changing the starter quest.
7. Fail closed before marking protection complete when the arrival biome cannot
   be identified or the protection marker cannot be verified. Preserve the
   already-completed safe relocation and record protection failure separately.
8. Emit bounded sanitized evidence: selected point, actual biome, selected
   family/mask, timer state, removed-family result, unrelated-family result,
   and final outcome. Do not log player names, platform IDs, or save contents.
9. Use the same persisted initial-biome value to filter the opening-trader
   registry before distance comparison.
10. Compute the bounded legal same-biome candidate set, reserve the exact
    opening quest route before mutating it, and complete it only after
    destination readback proves the expected same-biome trader.
11. Never change the destination again after completion, including after later
    biome travel or reload.
12. Preserve the native quest unchanged when no legal same-zone trader can be
    proven. Mark the attempt terminal so reload cannot reroll it. The failure is
    explicit and bounded, not a cross-zone fallback.

## Ordered implementation plan

### Gate 1 — freeze predecessor behavior

1. Add regression fixtures for the existing Snow value `8` behavior and the
   `HRS_TRADER_006` quest path.
2. Require exact quest ID, phase, objective ID, native rewards, and the five
   Snow-family names to remain unchanged.
3. Prove Standard, unrelated saves, and unchecked Random remain no-ops for
   protection; Standard and unrelated saves receive no trader mutation.

### Gate 2 — add failing 1.2.0 contracts

1. Define the five initial-biome identities and four protection-family bits.
2. Require Pine to persist initial-biome routing authority with no protection
   family or timer write.
3. Define all four five-buff families and their timer/max pairs.
4. Require exactly one-family mutation for Starting-biome-only mode.
5. Require same-biome trader filtering before deterministic X/Z distance and
   stable tie ordering.
6. Require a terminal no-trader/write/readback failure with native restoration
   and no reload retry.
7. Require relocation, protection, and trader outcomes to be independently
   reportable.

### Gate 3 — implement immutable arrival-biome state

1. Resolve the biome only after the primed landing produces the required
   grounded stable samples.
2. Validate it against the installed biome authority.
3. Persist the initial biome once and read it back.
4. Derive the optional protection family from that stored value.
5. Complete the relocation once; do not derive the initial biome again from
   later player position.

### Gate 4 — generalize the Snow suppressor

1. Move the proven Snow names and timer pair into a fixed reviewed family table.
2. Add Burnt Forest, Desert, and Wasteland using the identical narrow loop.
3. Reject unknown, zero-for-dangerous, multi-bit, or mismatched state.
4. On update/reload, maintain only the stored family when the exact policy and
   completed relocation remain valid.
5. Never write the native global `BiomeProgression` option.

### Gate 5 — constrain the working trader route

1. Keep the `HRS_TRADER_006` full-session journal observation and exact
   quest/phase/objective matching.
2. Start from the reviewed current-world trader set.
3. determine each candidate's actual biome;
4. retain only candidates matching the persisted initial biome;
5. choose nearest by planar distance with stable tie ordering;
6. reserve before changing the objective;
7. use native `SetLocation` and journal refresh;
8. read the destination back before Completed; and
9. restore the original objective and enter terminal failed-closed state if
   writing, refresh, readback, or marker completion fails.

For this Navezgane gate the five version-pinned placements remain the reviewed
trader authority. Replacing them with dynamic random-world registry discovery
belongs to the later random-world compatibility gate.

### Gate 6 — build QA forcing and evidence export

1. Force exactly one certified stable ID per fresh case without changing the
   production allowlist.
2. Emit separate bounded biome and trader snapshots plus the common relocation
   identity.
3. Hash every exported file and record setup-invalid cases separately from
   product failures.
4. Run static/state tests, deterministic double compilation, deployment
   checks, package identity checks, and clean rollback before live play.

### Gate 7 — execute the five games

Run Pine, Snow, Desert, Burnt Forest, then Wasteland. Pine first detects broad
or accidental protection writes. Snow second compares directly with the
working predecessor. Introduce and diagnose only one new family at a time after
those controls pass.

### Gate 8 — player-facing and random-world follow-up

After the isolated five-game matrix passes, run one normal-enemy player sample.
Then use a separately generated random world to prove dynamic POI/trader
discovery before expanding compatibility claims beyond Navezgane. Random-world
failure does not invalidate the Navezgane 1.2.0 proof; it limits release scope.

## Live procedure for each case

Use a new Navezgane game with the exact case name. Use enemies off to isolate
biome-hazard behavior; the separate player-experience sample retains normal
enemies. Keep collision on, fly/noclip off, and God mode off so health and
hazard effects remain meaningful.

1. Select Random and enable only `Starting biome only`.
2. Arm the QA harness for the case's single certified stable ID.
3. Start the fresh game and observe the primed landing.
4. Within five seconds of grounded completion, capture actual biome, active
   hazard buffs, protected marker/mask, relevant timer/max, health, and point.
5. Observe the opening quest and capture eligible trader candidates, their
   biomes/distances, the selected same-zone trader, objective destination
   readback, and completed one-time route marker.
6. Remain in the arrival biome for at least 210 seconds, exceeding the native
   180-second first-spawn hazard timer.
7. Confirm the protected hazard never becomes active and health/progression
   remain ordinary.
8. Save, exit, reload once, and observe for another 30 seconds. Protection and
   trader destination must persist without another relocation or route event.
9. After the initial-zone evidence is complete, use a clearly labeled QA-only
   observation transfer into a different dangerous biome. Confirm that biome's
   ordinary hazard is active/advancing and the opening trader remains the
   original initial-zone destination.
10. Export the case evidence before creating or arming the next game.

## Pass criteria

A dangerous-biome case passes only when:

- requested point and actual grounded point are the expected stable ID;
- runtime-detected biome matches the case;
- exactly one expected protection family is persisted;
- that family's five buffs are absent immediately, through 210 seconds, and
  after reload;
- its timer remains at the native maximum;
- the other three family timers/markers are not rewritten;
- the selected trader is valid, inside the actual initial biome, and nearest
  among valid same-zone candidates;
- the phase-one quest destination readback matches that trader;
- the quest ID, phase, rewards, state, and progression remain native;
- health, starter quest, inventory, and exactly-once state remain valid; and
- reload does not teleport or route again; and
- later entry into another dangerous biome retains that biome's ordinary
  hazard and does not change the initial-zone trader destination.

The Pine Forest control passes only when the landing succeeds, no dangerous
family is selected or removed, no dangerous timer is rewritten, the phase-one
quest routes once to Pine Forest Trader Rekt, progression is normal, later
dangerous-biome entry retains its normal hazard, and reload does not relocate
or reroute.

Any setup mismatch, wrong save, wrong forced ID, God/fly state error, or QA
tool failure is invalid setup evidence and does not reject the certified point.

## Evidence packet

Each case must preserve:

- exact 1.2.0 DLL and ModInfo identities;
- arm/forced-ID identity and fresh game name;
- sanitized chronological runtime events;
- immediate, 210-second, and post-reload protection snapshots;
- registered trader candidates with biome and distance, selected trader,
  objective readback, and route-marker snapshots;
- later-biome hazard and unchanged-trader observation;
- operator observation and optional screenshot;
- pass/fail reason and rollback disposition; and
- SHA-256 for every exported evidence file.

The cycle summary must distinguish static contract success, controlled live
success, and player-facing release approval.

Use one compact row per game with independent fields:

| Field | Required value |
| --- | --- |
| Setup | Valid or invalid with reason |
| Landing | Stable ID, requested biome, actual biome, grounded result |
| Protection | Pass/fail/not applicable, family, five-buff result, timer result |
| Trader | Pass/fail closed, candidates, selected ID, distance, readback |
| Persistence | Post-reload markers, no relocation, no reroute |
| Isolation | Different dangerous family remains native; trader unchanged |
| Overall | Pass only when every required domain passes |

## Planning completion decision

Planning is complete when the predecessor regression fixtures, new state
contract, exact four-family table, same-biome trader rule, five forced cases,
evidence schema, and rollback conditions are represented by failing automated
contracts. Coding may then proceed in the gate order above. Live QA may begin
only after those contracts pass against a deterministic 1.2.0 candidate and
the game is closed for verified staging.

## Deferred companion scope

`All dangerous biomes` is a separate policy and test matrix. It may reuse the
same five locations after `Starting biome only` passes, but it must prove all
four families are suppressed without weakening the single-family isolation
contract. Trader selection still uses only the immutable initial biome.

Although each five-game case observes both outcomes end to end, implementation
and evidence retain separate protection and trader result fields. A trader
failure cannot be reported as a biome failure, and a biome failure cannot be
reported as a trader failure.
