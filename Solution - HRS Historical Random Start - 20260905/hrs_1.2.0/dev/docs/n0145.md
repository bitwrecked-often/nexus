# Historical Random Start — Client/QA Requirements and BAT Start

Date: 2026-08-27
Applies to: stamped QA2 package derived from `0.0.5-alpha-tech-demo`

## Plain-language contract

The development workstation owns source editing, compilers, builds, and
repairs. A client or QA laptop does not need that toolchain. It receives a
frozen package containing the already-built, hash-pinned main runtime and
starts the existing manager by double-clicking the package-root BAT.

The root QA BAT is only a friendly doorway into the established manager. It is
not another launcher pipeline, installer authority, runtime entry point, or
main function.

## Client/QA laptop requirements

- 64-bit Windows 10 or Windows 11 desktop.
- Steam and 7 Days to Die installed and able to run normally.
- The current supported non-EAC game build. For this QA candidate,
  `Assembly-CSharp.dll` must have MVID
  `326ffd03-1d6d-4efb-a7dc-79201537b1c3`.
- Windows PowerShell 5.1 with Windows Forms and System.Drawing. These are
  ordinary built-in Windows desktop components.
- Permission for the signed-in user to create the mod-owned
  `Mods/mod` folder beneath that game install.
- The QA package fully extracted directly beneath the `7 Days To Die` folder.
  Do not run it from inside the ZIP.
- Steam running and the game closed before pressing Apply.
- A new, not-yet-created game name chosen exactly and used identically in the
  manager and the game's New Game screen.

If Windows displays an `Unblock` checkbox in the downloaded ZIP's Properties,
select it before extraction. The BAT uses a process-only execution-policy
bypass so it can start its packaged PowerShell manager; it does not change the
machine's system execution policy.

## Not required on a client/QA laptop

- .NET SDK, Roslyn, Visual Studio, VS Code, or another compiler;
- Git, GitHub Desktop, Python, Codex, ChatGPT, or another AI/development tool;
- a Nexus development key;
- the development workstation's private target record; or
- permission to edit source, rebuild the DLL, repair the candidate, alter
  saves, or change the game itself.

## Start and test sequence

1. Verify the downloaded ZIP SHA-256 against its adjacent checksum file.
2. Extract the dated QA2 folder directly under the game's installation root.
3. Open that extracted folder and double-click
   `START_HISTORICAL_RANDOM_START_QA.bat`.
4. Enter the exact name of a game that does not exist yet.
5. Select `Random`, press `Apply`, and confirm.
6. The manager verifies the installed game MVID and both packaged payload
   hashes before installing the main runtime. A mismatch stops the operation.
7. Launch the game through the manager or the normal non-EAC route.
8. Choose New Game and enter the exact same armed name.
9. Record the selected candidate, native position, final position, lifecycle
   chronology, marker, and hashes for the QA report.

Known-good operator route:

`BAT -> existing manager -> arm exact not-yet-created name -> Random -> Apply -> non-EAC launch -> New Game -> exact name -> one deferred placement -> settling verification -> Completed or fail-closed evidence`

## What the BAT/package may change

On confirmed Apply, the established manager may install only:

- `Mods/mod/d0163.dll`;
- `Mods/mod/ModInfo.xml`; and
- the mod-owned `Bridge/policy.v1.json` state required by the selected exact
  game name.

It must not install DevProbe or MarkerProbe, alter a save, edit game files,
disable EAC, build source on QA, or start a second placement pipeline.

## Stop conditions

Stop and report to DEV if the BAT reports a game-build mismatch, missing or
changed payload, unsafe existing destination, permission error, or any other
blocked Apply. QA records the evidence; QA never refreshes the MVID pin,
rebuilds, or patches the frozen package.
