# Historical Random Start development story and framework-adaptation record

Date: 2026-09-01
Scope: project history through the opening of HRS 1.2.0
Purpose: explain what was attempted, what the game actually did, why the method
changed, what evidence supports each decision, and what later developers must
preserve

## How to read this record

This is the narrative route through the detailed manifests and evidence. It
does not replace their exact hashes, test results, or acceptance boundaries.
When this story and a version-specific manifest differ, the exact manifest for
the artifact under test is authoritative.

Three evidence labels are used deliberately:

- **Documented game evolution** means an official Fun Pimps source or a
  versioned installed-file comparison supports the change.
- **Observed current-framework behavior** means our static inspection or live
  QA proved how the installed target behaves, but not necessarily when or why
  The Fun Pimps introduced it.
- **Project adaptation** means the HRS method changed because of that evidence.

Do not turn an observed behavior into a claim about a specific Fun Pimps
internal change unless a source comparison actually proves it.

## The original idea

Historical Random Start is inspired by the older Alpha 6–17.4 experience in
which new players could begin at different authored random spawn points. The
official Alpha 6 notes describe multiple new-player starting locations and a
random-spawn rule. Later player evidence contrasts Alpha 17.4 with Alpha 18,
where a repeated world name/seed could produce the same opening location.

That history defines the experience we want, not an instruction to copy old
code. HRS uses the current game's supported events, player state, terrain,
quest, and mod-loading framework to recreate the useful player outcome.

Primary historical evidence: `dev/evidence/n0013.md`.

## Chronological development and method changes

### 1. Start with the modern native spawn framework

The first V3.1 inspection found a promising supported path:

- `PlayerSpawnedInWorld` identifies the spawn lifecycle;
- the local authoritative server can resolve the player entity;
- `GameManager.GetSpawnPointList()` exposes authored points;
- `CanPlayersSpawnAtPos` checks loaded ground, water, collision, and headroom;
- per-character custom variables provide serializable exactly-once state; and
- `SetPosition` can perform the bounded authoritative placement.

The initial strategy was intentionally small: use the game's own authored
spawn list, place only a genuinely new character, verify the final position,
and never alter vanilla world or save files directly.

Evidence: `dev/evidence/n0011.md`, `dev/evidence/n0014.md`, and
`dev/docs/n0009.md`.

### 2. Native authored randomness did not provide geographic variety

**Observed current-framework behavior:** repeated use of the native authored
selector clustered starts around the central green region. The API could pick
randomly, but the available authored list was not geographically broad enough
to create the old-style biome and edge variety.

**Project adaptation:** HRS retained the native lifecycle and safety concepts
but introduced a mod-owned, reviewable Navezgane catalog. Selection authority
was kept as an explicit allowlist so adding a coordinate could never make it a
production spawn by implication.

This is why the project distinguishes catalogued, carousel tested, certified,
and explicitly promoted points.

Evidence: `dev/docs/n0230.md`, `dev/docs/n0233.md`, and the 1.1.0
`dev/evidence/carousel/HANDOFF_CATALOG.md`.

### 3. Distant placement exposed chunk and observer limits

Early direct placement and verification repeatedly encountered unloaded remote
terrain. We tried progressively narrower interpretations of the current APIs:

1. broad `World.IsChunkAreaLoaded` readiness;
2. the candidate's containing chunk only;
3. player and existing-observer synchronization; and
4. an observer-first preload that left the player at the vanilla start.

Inspection showed that `IsChunkAreaLoaded` can require neighboring chunks, not
merely the candidate's containing chunk. More importantly, live QA showed that
moving only the existing observer did not make the remote target ready within
the bounded deadline. `ChunkObserver.SetPosition` changes desired observer
position; it is not itself a synchronous chunk-generation command.

**Project adaptation:** do not pretend an observer move is a completed preload,
do not block or force the provider, and do not loop indefinitely. Move player
and existing observer together in a bounded reversible transaction, let the
normal chunk manager work, and restore the original position on failure.

Evidence: `dev/evidence/n0045.md`, `n0049.md`, `n0051.md`, `n0095.md`, and
`dev/docs/n0233.md`.

### 4. Memorable roofs and interiors were not safe starting assumptions

The owner surveyed a dramatic Perishton rooftop. The coordinate was accurate,
but live arrival occurred before all relevant prefab collision was dependable:
the player fell through the floor, became trapped, and died. Raising nominal Y
by three metres changed the symptom but not the underlying timing.

The original approximate city point could likewise resolve inside or on a POI.
Moving NG01 to an ordinary street and constraining its local search produced a
repeatable grounded arrival.

**Project adaptation:** prefer open street-level or clearly supported surfaces;
derive landing height from the loaded world; classify roofs, interiors, water,
cliffs, props, and narrow prefab edges separately; and require the observed
grounded position rather than trusting authored Y.

Evidence: `dev/docs/n0233.md`.

### 5. The landing became a reversible, exactly-once transaction

The reliable core sequence became:

1. validate exact build, world, local authority, EAC state, lifecycle, policy,
   and new-character eligibility;
2. reserve a per-character marker;
3. make one bounded selection and preserve the vanilla position;
4. move player and existing observer together;
5. wait within a monotonic deadline;
6. resolve a safe loaded surface and require stable grounded samples; and
7. complete once or restore the preserved position and stop.

This architecture was created by the failures above. The Reserved marker is
deliberately consumed on ambiguous failure so reload cannot turn uncertainty
into repeated teleports.

Evidence: `dev/docs/n0233.md` and runtime files `c0167.cs` and `c0181.cs`.

### 6. Modern biome progression made dangerous starts a separate problem

**Documented game evolution:** the modern game contains lethal biome-progression
hazards and exposes a whole-world `BiomeProgression` sandbox setting. Official
Fun Pimps V2.0–2.4 development material describes these biome hazards and the
global option. This is not the same design surface as the older random-start
experience.

**Observed current-framework behavior:** each dangerous biome uses a distinct
root/timer/recovery family. The global setting affects the whole world; it
cannot express “protect only this relocated character's starting biome.”

**Project adaptation:** do not change `BiomeProgression`, vanilla XML, weather,
temperature, enemies, or ordinary damage. Use exact-game RandomSafe authority,
the completed relocation marker, and one per-character family value. The first
working example stored Snow family `8`, removed only the five reviewed Snow
hazard buffs, and maintained only the Snow timer at its native maximum.

The owner observed the intended immediate Snow landing without the unwanted
starting debuff. The older record still correctly leaves the longer duration,
reload, death, unrelated-save, and removal matrix open. HRS 1.2.0 generalizes
the working narrow mechanism and completes that missing proof.

Evidence: `dev/evidence/n0018.md`, `dev/docs/n0231.md`, and `n0233.md`.

### 7. The native starter quest still assumed Pine Forest

**Observed current-framework behavior:** Journey to Settlement uses phase-one
`Goto` objective `trader` with `OnlyBiome / pine_forest`. That is reasonable for
the normal start, but a relocated Snow, Desert, Burnt Forest, or Wasteland
player can be sent far away merely to begin trader progression.

Static API inspection suggested a narrow solution: listen for the exact quest,
change only its destination with native `ObjectiveGoto.SetLocation`, refresh
the journal, and leave quest creation, interaction, rewards, and later
progression to the game.

Evidence: `dev/evidence/n0019.md` and `dev/docs/n0232.md`.

### 8. Quest lifecycle timing forced several trader-method changes

The final trader method came from a sequence of falsified assumptions:

| Attempt | What the installed game did | Method change |
| --- | --- | --- |
| Subscribe to `QuestAccepted` after relocation | V3.2 could auto-accept the quest before relocation verification and subscription | Keep the event, but inspect the existing journal too |
| One immediate `FindLatestNonSharedQuest` lookup | The UI could display the quest while this helper returned none | Observe the bounded journal list instead |
| Short frame-count window | Tutorial completion is player-paced; high FPS exhausted the window first | Observe for the full eligible session |
| Case-sensitive XML ID match | Runtime quest identity casing differed | Preserve the ID and use `OrdinalIgnoreCase` |
| Faction-specific `GetTraderList` | Returned empty while the vanilla destination existed | Test the journal's broader trader collection |
| Journal `TraderPOIs` after reload | Also transient/empty after destination persistence | Use five version-pinned Navezgane placements and prefab bounds |
| Custom destination write | Native `SetLocation` plus `RefreshQuest` changed only the intended objective | Retain this successful native path |

These are **observed V3.2 framework behaviors**. The repository does not prove
the exact Fun Pimps release or internal commit that introduced each one.

`HRS_TRADER_006` then completed:

`NG01 -> RELOCATION_COMPLETED -> TRADER_ROUTE_RESERVED -> TRADER_ROUTE_SELECTED -> TRADER_ROUTE_COMPLETED`

The route changed from the roughly 2.4 km Pine Forest destination to the
closest reviewed trader without fallback or exception, while retaining native
tutorial completion and quest progression.

Evidence: `dev/docs/n0232.md`, `n0233.md`, `n0234.md`, and `n0235.md`.

### 9. Packaging identity became part of functional QA

QA rejected 1.0.0 because package notes and fingerprints did not identify the
DLL consistently, even though the intended functional DLL was present. This
was a release-identification defect that made forensic comparison unreliable,
not a gameplay defect.

**Project adaptation:** 1.0.1 synchronized ModInfo, manager pins, runtime log
identity, release notes, verified hashes, and deterministic build output. A
feature is not handed off unless QA can prove which exact bytes produced it.

Evidence: `dev/docs/n0234.md`, `n0235.md`, root `CHANGELOG.md`, and the release
identity contracts.

### 10. The carousel converted human observation into repeatable screening

Manual scouting found candidate POIs and coordinates, but screenshots alone
could not prove collision timing or a true grounded landing. The QA carousel
automated repetition while retaining the operator for visible game context.

The method evolved to use stable IDs, collision on, fly off, controlled God
mode, a primed second placement two metres above resolved terrain, grounded
samples, a dwell interval, first-failure halt, exact-instance rejection, and
compact event/result evidence.

The second placement recovered some initially unstable arrivals, but it did
not convert a floating, embedded, falling, hostile-occupied, or non-grounded
point into a pass. “On the ground” remained game-reported authority. This is
why the human stayed in the loop even after automation became possible.

The final controlled certification passed 171/171 survivors in two runs. That
proves landing health for those exact Navezgane instances, not biome protection,
trader routing, arbitrary random-world placement, or release promotion.

Evidence: the 1.1.0 `dev/evidence/carousel/HANDOFF_CATALOG.md` and
`dev/docs/n0238.md`, `n0239.md`, and `n0240.md`.

### 11. The carousel landing lesson moved into production

The 1.1.0 candidate adopted the proven primed transaction without shipping the
QA runner: first placement, chunk wait, two-second prime, loaded terrain
resolution, second placement two metres above the result, three grounded
samples, then adoption of the actual settled surface.

During this work the installed `Assembly-CSharp` MVID changed. Runtime guard,
build references, manager, tests, and release record were repinned before
another candidate was accepted. This proves a binary/framework identity change;
it does not by itself prove that a particular API signature changed.

The shared checker also expected the older project catalog's X/Z constructor
while the primed catalog carried X/Y/Z. That was a project schema evolution,
not a Fun Pimps framework change. The checker became version-aware rather than
weakening either contract.

Evidence: `dev/docs/n0239.md` and `n0241.md`.

## Current 1.2.0 continuation

HRS 1.2.0 deliberately builds from working examples:

- retain the Snow per-character suppressor and generalize it to the other
  three reviewed dangerous families;
- retain the `HRS_TRADER_006` journal observer and native objective-write path;
- persist the actual final grounded initial biome once;
- use that immutable biome for the protection family and trader filter;
- choose the nearest valid trader only inside that biome;
- never reroute because of later travel, death, reload, or reconnect; and
- score relocation, protection, and trader routing separately.

The five Navezgane games prove this integration one biome at a time. Dynamic
trader discovery for player-generated random worlds remains a later gate,
because the successful pinned-placement trader path is Navezgane-specific.

Current plan: `dev/docs/n0242.md`.

## Rules future developers must preserve

1. Reinspect and fingerprint the installed build before trusting an old API,
   XML name, buff family, quest definition, prefab placement, or compiler
   reference.
2. Label conclusions as official history, installed-build inspection, live
   observation, operator report, or inference.
3. Reuse a working native path until evidence requires changing it.
4. Preserve failed hypotheses and explain why the next method differs.
5. Keep relocation, protection, trader routing, packaging identity, and QA
   setup as separate failure domains.
6. Never promote a location, map type, family, or compatibility claim because
   adjacent work passed.
7. Preserve exact game names, stable IDs, artifact hashes, MVIDs, policy
   digests, event order, and result hashes.
8. Use native APIs narrowly; do not globally patch vanilla XML for a feature
   intended for one eligible character and game.
9. Re-prove transient registries, early callbacks, loaded chunks, and prefab
   collision after a game update.
10. Combine automated state evidence with the human operator's visible geometry
    and gameplay observation.
