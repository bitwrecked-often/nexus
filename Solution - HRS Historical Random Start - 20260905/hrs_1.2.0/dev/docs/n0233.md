## Executive summary

This development run moved Historical Random Start from a compact-path rebuild
of the `0.0.5` technical demonstration into a functional curated-start system
with a portable PowerShell 5.1 manager, reversible relocation, live Navezgane
QA, and an optional snow-hazard safeguard tied to an exact-game policy.

The most important result was not a large quantity of code. It was discovering
the correct order of operations and the boundaries the game will tolerate.
Ground-level curated starts are reliable. Remote observer-only chunk loading is
not. High or interior POI starts can race prefab collision and trap or kill the
player. The validated Perishton street start therefore remains the controlled
NG01 proof point for `0.1.0-tech-demo`.

The current live snow-first runtime was built and staged from the predecessor
lane with hash:

`2CCB22C3394648FC783F05DEE74D1D47EB43A236570E5D0BD22C0CB680045363`

The new `hrs_0.1.0` solution identity and tests are saved, but its fresh
versioned DLL build remains pending because the game process restarted and the
build guard correctly stopped. Do not describe the new lane as sealed until
that deterministic build completes with the game closed.

## What changed

### Compact, portable solution layout

The working solution was reorganized around Windows PowerShell 5.1 and older
Windows path limits. User-facing files remain at the root while implementation
detail lives under `dev/`. Compact internal filenames and shallow routing avoid
the long/deep paths that previously prevented reliable execution.

The primary user experience is now:

- `START.bat` at the solution root;
- automatic validated game-root discovery with a folder-picker fallback;
- exact new-game-name policy binding;
- Standard or Random selection;
- an optional arrival-biome protection checkbox;
- no automatic game launch after Apply;
- visible status and recoverable deployment behavior.

The manager no longer depends on being stored at a fixed parent depth beneath
the game directory. The BAT can live elsewhere on the user's computer as long
as its solution payload remains together.

### Reversible relocation transaction

Random relocation now has a bounded transaction:

1. validate build, EAC state, single-player authority, lifecycle, world, and
   exact game-name policy;
2. reserve a per-character marker;
3. select one bounded candidate;
4. preserve the vanilla starting position;
5. move player and observer together to request destination loading;
6. resolve a native safe landing within the point's permitted radius;
7. verify chunk availability, position tolerance, and stable grounded samples;
8. mark completion exactly once; or
9. restore player and observer to the preserved position on failure.

Follow-up spawn callbacks cannot overwrite the transaction's final result.
Logs use bounded reason codes and curated IDs instead of raw private paths or
unbounded game state.

### Snow-first arrival-biome protection

The main manager now includes an unchecked option:

`Protect the arrival biome hazard (snow proof)`

Unchecked Random retains complete vanilla biome hazards. Checked Random writes
the signed internal `RandomSafe` mode for the exact new-game name. After a
verified NG01 relocation completes, runtime stores:

`bitwrecked_hrs_biome_v1 = 8`

Only a character with both the Completed relocation marker and snow family `8`
is eligible. The runtime suppresses the native snow hazard family and restores
its timer while leaving these systems alone:

- visible weather and ordinary temperature;
- zombies and POI danger;
- falls and ordinary damage;
- hunger, thirst, infection, and injuries;
- trader, challenge, XP, inventory, and equipment state;
- desert, burnt-forest, and wasteland hazard families;
- Standard games and unrelated saves.

This is a live-QA proof, not a claim that every biome family is complete.

## QA sessions and observations

### Early authored-point behavior

The game's original authored random-start list clustered around the central
green region. Repeated tests appeared close to the normal starting area, which
confirmed that calling the native selector alone would not provide the desired
biome and edge variety.

### NG05 western island

The first island attempt timed out while trying an observer-only remote load.
A later reversible attempt reached shallow water. The water landing was
deliberately retained as a novel curated possibility rather than treated as an
automatic defect. It still needs dedicated drowning, shore-distance, and
underwater-start QA before the full pool opens.

### NG01 initial city approximation

The original approximate Perishton anchor could resolve inside or on top of a
structure. Verification detected a position mismatch and restored the player.
Review of the Navezgane road mask moved the controlled anchor to the proven
street corridor and limited local drift to eight meters.

### Successful street cases

Fresh controlled games, including `HRS_NG01_003`, demonstrated the outdoor
street arrival and a completed persisted relocation marker. Later runs reused
the controlled Perishton experience while investigating more dramatic starts.

### Rooftop experiment

The player manually surveyed a memorable Perishton rooftop at approximately:

- position: `-1554.3, 101.3, 1824.5`;
- facing: approximately `254.4°`;
- intent: begin just outside the aggro range of two visible zombies.

The exact X/Z point and zero-radius fallback were implemented. In live QA the
player fell through an incompletely loaded floor into the first level and died
behind locked doors. Raising the nominal arrival by three meters did not solve
the underlying prefab/collision timing problem.

### Observer-first preload experiment

We then implemented a true two-phase experiment: leave the player at the
vanilla start, repeatedly move only the chunk observer, require eight stable
safe-position samples, and relocate afterward. `HRS_NG01_006` produced:

`CANDIDATE_LOAD_REQUESTED → 30 second wait → CANDIDATE_LOAD_RESTORED → VERIFY_CHUNK_TIMEOUT`

Conclusion: this client does not load the distant destination chunk merely
because the player's observer is repeatedly moved there. The experiment failed
safely and was archived. It should not be revived without a different proven
native chunk-loading mechanism.

### Return to known-good street build

Source and runtime were returned to the street configuration. Deterministic
recompilation reproduced the prior known-good hash byte-for-byte:

`0CE6BE64FA53CFCFC11B053C1304BE0B4D19448F7E93F40E26074A90E8CE9413`

That exact reproduction proved the rollback restored the intended source, not
merely a similar behavior.

## Engineering and safety practices retained

- No vanilla world, save, `Data/Config`, or game executable was edited.
- Live staging occurred only after checking that the game was closed.
- Each meaningful live DLL replacement received a full recoverable capsule
  backup under the predecessor lane's `dev/tmp` directory.
- Bridge policy and result files were preserved during DLL-only staging.
- Deterministic double compilation was required before staging.
- Compatibility remains pinned to the installed `Assembly-CSharp` MVID.
- EAC builds fail closed.
- Standard remains a no-relocation/no-protection path.
- Exact game names bind launcher intent to runtime authority.

## Known limitations

1. The curated selector is intentionally forced to NG01 for controlled QA.
2. Only snow family `8` is implemented for arrival-biome protection.
3. Rooftop and interior POI starts are not supported by the current loading
   sequence.
4. NG05 water arrival needs dedicated survivability validation.
5. Trader continuity is designed but not implemented.
6. Random-world generation and multiplayer are not release claims.
7. The current result schema reports relocation completion but does not yet
   expose a separate user-facing protection-result field.
8. The GUI uses the internal mode name `RandomSafe` in policy data; player copy
   should continue describing this as optional arrival-biome protection.

### 2026-08-28/29 — Pine Forest restriction confirmed

Installed V3.2 quest XML confirms that
`quest_whiteRiverCitizen1` phase one uses `biome_filter_type="OnlyBiome"` with
`biome_filter="pine_forest"`. This is the direct cause of distant Random-start
characters being routed back toward a forest trader.

The project will use that exact filter as the intervention boundary, not edit
or delete it globally. Standard and unrelated games retain the native Pine
Forest selection. Only a character with an exact matching Random policy,
Completed relocation marker, Pending trader-route marker, and the exact active
phase-one `trader` objective may receive the closest registered trader across
any biome. If any gate or native update fails, the existing Pine Forest
destination remains the fallback. Phase two already uses the closest trader
and is intentionally untouched.

### 2026-08-28/29 — First trader candidate missed auto-accepted quest

`HRS_TRADER_001` relocated successfully and logged `TRADER_ROUTE_READY`, but no

retains the event subscription and immediately checks the existing journal via

ID, phase-one, `trader` objective, authority, relocation, and Pending-marker
gates. No quest is created, reset, or retried.
