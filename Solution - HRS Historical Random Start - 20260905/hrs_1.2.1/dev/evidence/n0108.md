# Phase 1A Post-Placement Player/Observer Drift Analysis

Date: 2026-08-20
Decision: Native post-callback spawn overwrite identified; no state changed

The owner authorized read-only analysis after containing-chunk readiness timed
out. No source, payload, live mod, save, or game process was changed.

## Exact native ordering

Pinned `Assembly-CSharp.dll` IL establishes this order inside
`PlayerMoveController.updateRespawn` for the new-game lifecycle:

1. the local entity is marked spawned;
2. `GameManager.PlayerSpawnedInWorld(...)` is called;
3. that method synchronously invokes `ModEvents.PlayerSpawnedInWorld`;
4. the Phase 1A handler currently reserves, selects, captures semantics, calls
   the one player placement, and synchronizes the observer;
5. control returns to the same native `updateRespawn` invocation;
6. native respawn finalization later resets last-tick/transform state; and
7. at IL `0x0B71`, it calls virtual
   `Entity.SetPosition(spawnPosition.position, true)` again using the original
   native spawn position.

The native final write occurs after the mod callback. On subsequent updates,
`EntityPlayer.Update` calls
`ChunkObserver.SetPosition(player.GetPosition())`, propagating the restored
native position into the observer. `DetermineChunksToLoad` therefore does not
receive a persistent candidate position.

## Runtime corroboration

Without publishing coordinates or player identity, aggregate/categorical
inspection establishes:

- the normally saved final player position equals the native spawn-event
  position;
- the attempted candidate cannot equal that native position, because its
  containing chunk remained absent while the native spawn position was already
  loaded; and
- the containing-chunk timeout is therefore explained by the post-callback
  native overwrite, not by failure of `SetPosition` itself.

This is direct agreement between native IL ordering and the closed-run state.

## Smallest lifecycle-aligned correction

Use the spawn event only to validate, reserve once, select once, and retain the
candidate/context in memory. Defer the actual mutation until the first
`ModEvents.GameUpdate` callback after the spawn handler has returned:

1. revalidate the same world/entity/context and existing observer;
2. capture the semantic-before snapshot at that deferred instant;
3. call player `SetPosition(candidate, true)` exactly once;
4. synchronize the same existing observer exactly once;
5. start the existing 30-second containing-chunk verification deadline; and
6. preserve all safety, position, semantic, and Completed gates.

Because a later `GameUpdate` callback cannot run inside the still-active
`PlayerSpawnedInWorld` handler stack, the native final spawn-position write has
completed before deferred placement. This adds no second selection, second
placement, explicit chunk request, observer lifecycle operation, retry, reroll,
rollback, teleport, respawn, or marker repair.

The failed target remains Reserved and must not be reused.
