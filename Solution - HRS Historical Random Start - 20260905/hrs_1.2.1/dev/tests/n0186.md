## How to read this matrix

These cases define expected behavior. `Pending` means no evidence has been
collected; it is not a pass. Tests may first run against pure model fixtures,
then against a staged disposable helper after the Phase 1A build gate exists.

Every failure must preserve the normal game spawn or remain inside the
launcher's read-only state. No test may use the live `Mods` folder, live saves,
worlds, XML, Harmony, or a public package.

## Required assertions for every runtime case

Each runtime test must record, without private identity data:

- target build/runtime fingerprint;
- policy mode and activation enum;
- lifecycle event class;
- authority result;
- marker state before and after;
- bounded attempt/wait/time counters;
- outcome (`Relocated`, `VanillaFallback`, or `Rejected`); and
- exact sanitized reason code.

The test must also verify that no forbidden file, process, network, registry,
service, task, or game-payload side effect occurred. A successful relocation
alone is not a passing result if the boundary audit fails.

## Evidence and promotion rules

Pure model cases may be automated without a game process. Runtime cases require
an approved disposable target: either a staged copy or the one exact
owner-designated customer-grade lab carrying the complete private approval
record. The build/output stage remains external in both cases. Runtime evidence
must identify what was actually observed and prove that existing saves, Mods,
Harmony, game files, and project files remained unchanged. No row becomes
`Pass` from code inspection alone when the contract requires live behavior,
timing, client synchronization, or save survival.

Phase 0A is not accepted while a required negative case is silently skipped,
marked pass without evidence, or used to justify widening a resource limit.
