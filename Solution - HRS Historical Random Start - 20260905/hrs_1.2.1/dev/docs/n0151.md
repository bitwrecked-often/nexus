# Historical Random Start - Alpha 6 Method DEV Test and Software Assurance Contract 0.0.1

Status: Required contract before the first project DLL is copied into any
owner-approved game test target

Scope: Current unpublished Historical Random Start - Alpha 6 Method solution only

Public/provider release authorization: No

## Purpose

Make every executable test artifact explainable, reproducible, bounded, and
removable from its first build. Provider readiness begins with the first DEV
binary; it is not paperwork added after a feature appears to work.

This contract combines the live-test wiring boundary with software supply-chain
and eventual provider-review requirements so source, binary, installation,
behavior, evidence, and rollback remain one traceable object.

## Governing Rule

No DLL, BAT, PowerShell tool, XML, configuration, or archive enters the live
game test path unless its source, build inputs, output hash, owned destination,
allowed behavior, test purpose, and removal procedure are recorded first.

Passing a local gameplay test does not authorize packaging. Passing a provider
scan does not prove gameplay safety. These are separate gates.

## DEV Artifact Identity

Initial owned test mod folder:

`mod_DEV`

The exact public product/mod folder name remains undecided. DEV identity must
stay visibly non-release and must not be silently relabeled into a public
archive.

The first Phase 1 probe may contain only:

- `ModInfo.xml`;
- one project-built probe DLL;
- a strict test configuration only if Phase 0A proves it necessary; and
- documentation or license files that the game loader ignores.

It contains no gameplay XML, custom buff, policy writer, installer, updater,
embedded executable, downloaded component, obfuscation, or unrelated library.

## Exact Phase 1 Behavior

The observation-only probe may:

- register the current `PlayerSpawnedInWorld` event;
- classify the current `RespawnType`;
- observe server/client authority;
- verify whether the player entity resolves;
- detect duplicate observations;
- record bounded sanitized timing and state evidence; and
- fail closed on incompatible build, target mismatch, or exception.

It may not:

- teleport or reposition any entity;
- generate a destination;
- add or remove a buff;
- set or remove a CVar;
- alter inventory, quest, XP, rewards, gamestage, health, or progression;
- deliberately write world, player, or save state;
- create a private log file;
- call a shell, network, registry, service, scheduled task, or external process;
- modify Harmony or patch a game method; or
- load on a non-allowlisted test target.

Its only diagnostic output is bounded sanitized entries in the normal game log.

## Test-Target Allowlist

Before installation, record one disposable target using:

- canonical save storage root;
- world name;
- game/save name;
- world GUID when available;
- intended local/listen/dedicated execution type; and
- backup identity/hash.

The probe must disable itself when the launched save does not match the exact
approved target. It must not broaden eligibility by partial name matching,
case-insensitive guessing, nearest-folder selection, or player identity.

Phase 1 begins local single-player or listen-server only unless a later test
record explicitly authorizes another target.

Do not parse, persist, or log Steam/platform IDs or player names to establish
the target.

### Owner-designated customer-grade lab class

The default and preferred deployment class remains `DisposableStagedCopy`.
For a private Phase 1 observation test only, the owner may instead designate
one exact installed Steam game root as
`OwnerDesignatedDisposableLiveInstall`. This is a runtime-target exception,
not a relaxation of build, ownership, save, or removal controls.

The exception is valid only when the private target record contains the exact
owner-approval object required by the target schema and all of these remain
true:

- compilation and payload assembly occur in a canonical project-owned build
  stage outside the installed game root, save root, backup root, and live
  `Mods`;
- game assemblies are referenced read-only from the exact fingerprinted game
  root and are never copied back, replaced, patched, or redistributed;
- the runtime copy may create only
  `Mods/mod_DEV/` after a separate approval names
  the exact payload inventory and hashes;
- only the exact new disposable world/game named by the target record may be
  exercised; existing saves and worlds remain out of scope and read-only;
- every pre-existing Mod, including `0_TFP_Harmony`, remains foreign,
  inventoried, and unmodified;
- `_game_dev_ai_tracking` and unrelated project/customer files remain
  protected;
- copy and load approval is artifact-specific and does not follow merely from
  designating the machine as a lab; and
- "disposable" describes the owner's recovery posture. It is not permission
  to wipe, reinstall, broadly delete, or remove foreign content. Any such
  action requires separate approval naming the exact target and operation.

An ordinary live root without the exact deployment class and complete approval
object must fail target validation. A staged-copy record may not carry the
owner exception.

## Compatibility Fingerprint

Every DLL build/test record must include:

- 7 Days to Die display/build version;
- Steam build ID when locally available;
- `Assembly-CSharp.dll` SHA-256;
- relevant TFP Harmony and loader versions, even when no patch is used;
- EAC enabled/disabled state;
- source revision or complete source-tree hash;
- compiler and SDK identity/version;
- target framework and architecture;
- dependency names, versions, origins, licenses, and hashes;
- output DLL name, size, timestamp, and SHA-256; and
- staged-package inventory and aggregate manifest hash.

Any inspected game-assembly change invalidates compatibility approval and
returns the artifact to review. The helper must fail closed rather than infer
that an updated method/event is equivalent.

## EAC and Cheat-Path Declaration

- Initial custom-DLL testing is no-EAC.
- No-EAC is not Developer Mode and does not authorize cheat commands.
- The project uses no Developer Mode, console teleport, cheat flag, encoded
  command, or debug invulnerability.
- The DEV `ModInfo.xml` must skip safely under anti-cheat rather than attempt an
  unproven load.
- EAC compatibility, achievements, rewards, and provider trust are separate
  claims that require direct evidence.
- Existing `0_TFP_Harmony` files remain unmodified.

## Source and Build Boundary

All active source, project files, build scripts, dependency declarations, and
test harnesses belong under this solution. Builds must occur from a clean
external staging/output directory owned by this project, never directly in
any game root or live `Mods`. An owner-designated lab may supply exact,
fingerprinted compiler references read-only; it may not be the build output
directory.

Required build properties:

- deterministic inputs and pinned dependencies;
- no dependency downloaded at game runtime;
- no secrets or tokens in source, build arguments, binaries, symbols, logs, or
  archives;
- no obfuscation, packing, encrypted payload, self-extraction, or self-update;
- no execution-policy bypass, elevation request, encoded PowerShell, or hidden
  process launcher;
- warnings treated and recorded rather than silently ignored;
- source and binary scanning performed on the exact staged artifact; and
- rebuild differences investigated before promotion.

If exact byte-for-byte reproducibility is not immediately achievable, document
the nondeterministic fields and require semantic/source-to-binary provenance
until the build is improved.

## Dependency and SBOM Record

Maintain a machine-readable and human-readable dependency inventory from the
first DLL. At minimum include:

- component name and version;
- direct or transitive role;
- upstream source;
- license;
- cryptographic hash of the consumed binary/package;
- whether it is supplied by the game, Windows, framework, or this project; and
- vulnerability/review status at build time.

Do not bundle game assemblies, Harmony files, Unity libraries, SDK caches, or
third-party binaries merely because the compiler referenced them.

The eventual release archive contains only redistributable files the project
owns or has reviewed permission to distribute.

## Behavioral Disclosure

Provider, scanner, reviewer, and user documentation must be able to answer:

- Why does the package contain a BAT, PowerShell tool, and/or DLL?
- Which component runs outside the game and which loads in the game?
- Which files can each component read or write?
- Does it use network, elevation, registry, services, tasks, startup entries,
  shell commands, telemetry, accounts, or automatic updates?
- Why is EAC disabled or the code skipped under EAC?
- What normal game APIs/events are used?
- How does the user remove every owned component?
- What remains in a save after runtime use?
- Which logs exist, where, and what private data is forbidden?

Answers must describe actual inspected behavior, not intent alone.

## Scanner-Friendly Engineering

Avoid behaviors commonly associated with false positives or unsafe installers:

- encoded or dynamically generated commands;
- runtime downloads;
- executing temporary binaries;
- process injection or memory patching without an explicitly reviewed need;
- broad recursive deletion;
- elevation or UAC prompts;
- registry/startup/service/task persistence;
- hidden background processes;
- credential or browser-token access;
- network callbacks or telemetry;
- misleading file extensions;
- packed/obfuscated assemblies; and
- archive contents outside the documented package tree.

Static scanner acceptance is evidence about the submitted artifact, not a
blanket guarantee for future builds. Every rebuilt archive receives new hashes
and review.

Do not upload private DEV artifacts to a third-party scanner that redistributes
samples unless the owner explicitly approves that disclosure. Provider-side
scanning and private/local scanning must be distinguished in evidence.

## Provider Access and Credential Safety

No GitHub, Nexus, Vortex, scanner, or provider token belongs in this project,
its logs, screenshots, scripts, configuration, archives, or support records.

If a provider requires source-repository access:

- use the provider's documented least-privilege integration or a narrowly
  scoped, revocable credential;
- provide access outside the shipped package;
- record what repository/scope was granted without recording the secret;
- revoke or rotate access after the review when appropriate; and
- never ask a customer to supply a developer credential.

Current provider-specific requirements must be verified against official
provider documentation at packaging time. This contract does not freeze a
provider's changing rules.

## Installation and Removal Ownership

Before every live test, produce an inventory containing source path,
destination path, size, and SHA-256 for each copied file.

The initial installation may create only:

`<selected game root>/Mods/mod_DEV/`

No installer may guess ownership, overwrite a foreign folder, modify the
existing Harmony folder, or copy files elsewhere.

For an owner-designated lab, inventory all existing top-level Mod folders and
record a pre-copy boundary manifest. Their presence does not authorize this
project to edit, disable, rename, move, or remove them. If the owned DEV
destination already exists and cannot be proven to match the approved project
manifest, installation stops.

Removal occurs only while the game is closed and removes only the verified
owned DEV folder after confirming its canonical path and expected manifest.
Unexpected or foreign files cause removal to stop and report rather than delete
them.

The BAT/design launcher under this solution is not automatically copied into
the game and is not a hidden installer.

## Backup and Rollback Gate

Before the first live load:

1. Close the game and verify no relevant process is running.
2. Identify the exact disposable world/game target and prove that no existing
   save is being repurposed.
3. If the target exists, create and hash a recoverable save backup. If it is a
   new target, record and hash a pre-test baseline proving the exact target is
   absent, plus the restore/removal procedure for only that new target.
4. Inventory the live `Mods` folder without changing it.
5. Inventory and hash the staged DEV payload.
6. Confirm the destination does not contain a foreign folder with the same
   name.
7. Record the game/assembly/EAC fingerprint.
8. Obtain explicit owner approval for the exact payload copy and exact runtime
   target. Lab designation alone is insufficient.

After the test:

1. Close the game.
2. Preserve required sanitized logs/evidence.
3. Remove only the verified DEV folder; removal of a created disposable test
   save is a separate exact action and is not implied.
4. Confirm the owned destination is absent.
5. Compare the save against the expected observation-only state.
6. Restore the backup if any unexplained state changed.
7. Launch once without the probe and verify ordinary behavior.

## Allowed Diagnostic Fields

Allowed:

- project/probe version;
- compatibility fingerprint summary;
- server/client authority classification;
- local/remote classification;
- `RespawnType`;
- entity resolution success/failure;
- duplicate/suppressed observation count;
- bounded state transition name;
- elapsed milliseconds; and
- sanitized exception category/message when it contains no private data.

Forbidden:

- Steam/platform IDs;
- player names;
- tokens or credentials;
- server addresses;
- raw `ClientInfo` serialization;
- full player/save snapshots;
- unrelated environment variables; and
- exact private paths in public/provider evidence.

## Abort Conditions

Stop testing and remove the DEV artifact if:

- it loads on an incompatible build or under an unapproved EAC state;
- it activates on a non-allowlisted save;
- reload, reconnect, death, or an excluded lifecycle appears eligible;
- duplicate observations cannot be bounded/suppressed;
- the observation-only probe changes player/gameplay/save state unexpectedly;
- the game crashes, hangs, or experiences unexplained material slowdown;
- logs expose identity, credentials, or unrelated state;
- source-to-binary provenance is incomplete;
- staged/live files differ from the approved manifest; or
- a scanner/provider flags the exact artifact and the finding has not been
  understood and resolved.

## Provider/Release Lanes

Keep these artifacts separate:

- DEV probe: private, disposable, explicitly non-release.
- Core candidate: authored-spawnpoint behavior only after runtime gates pass.
- Experimental expanded-Random candidate: separate label and evidence; never
  folded silently into the authored-spawnpoint core.
- Full local launcher/runtime package: includes only reviewed executable
  components and complete disclosures.
- Manager-compatible package: built only after the exact provider/Vortex archive
  contract is verified.
- Public source/review packet: contains no private logs, saves, tokens, recovery
  histories, game binaries, or provider credentials.

A no-scripts/no-DLL package cannot provide this runtime feature and must not be
presented as equivalent merely to satisfy a packaging convention.

## Evidence Required for Promotion

- clean source-tree inventory;
- parser/compiler/test output;
- dependency/SBOM record;
- source, binary, and package hashes;
- exact package tree;
- local malware/security scan evidence with tool/version/date;
- behavioral static review;
- test-target and backup record;
- install/remove before-and-after inventory;
- game log evidence sanitized for identity;
- compatibility matrix;
- known limitations and rollback result; and
- provider-specific validation evidence when that stage begins.

## Stop Boundary

This contract does not authorize building, copying, installing, launching, or
testing a DLL. Those remain separate actions after Phase 0A and staged-payload
review.

Owner designation of an installed game as a private lab changes only the
eligible runtime target class. It does not authorize a wipe, reinstall, edits
to existing saves or Mods, or use of an unreviewed payload.
