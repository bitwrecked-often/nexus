begin in the area where the player actually starts.

### Confirmed Pine Forest filter

The installed V3.2 `Data/Config/quests.xml` contains this exact phase-one
objective:

```xml
<objective type="Goto" id="trader" value="5" phase="1">
    <property name="biome_filter_type" value="OnlyBiome"/>
    <property name="biome_filter" value="pine_forest"/>
    <property name="nav_object" value="go_to_trader"/>
    <property name="allow_current_poi" value="true"/>

```

This is the confirmed reason an ordinary opening quest prefers a Pine Forest
trader. It also gives HRS a narrow and understandable intervention boundary:
for an eligible completed Random relocation, replace only this objective's
resolved destination with the closest registered trader across any biome.

Do not remove or patch this XML globally. A global XML change would also alter
Standard games, unrelated saves, and characters that never used HRS. The
runtime destination override preserves the native filter everywhere except the
one authorized relocated-character transaction.

## Eligibility gates

Custom routing may run only when all conditions are true:

1. the runtime build compatibility check passes;
2. authority is the approved local single-player, non-EAC server lane;
3. the signed policy exactly matches the active game name;
4. the policy uses an HRS Random mode;
5. the character has a valid Completed HRS relocation marker;
6. the exact opening quest, phase, and `trader` objective are active;
7. no valid completed or consumed trader-route marker already exists;
8. the authoritative post-relocation player position is available;
9. the native current-world trader registry can provide a bounded candidate
   set and a legal destination update mechanism.

Standard starts, unrelated saves, existing characters, later quests, death,
reload callbacks, and malformed state perform zero custom routing work.

## Selection rule

1. Query the game's authoritative current-world trader/POI registry.
2. Remove the Pine Forest biome restriction for this exact opening objective.
3. Admit only real trader POIs that can satisfy the normal turn-in.
4. Reject vending machines, arbitrary NPCs, test prefabs, disabled traders,
   missing POIs, out-of-world positions, and unresolved/custom candidates that
   cannot prove normal quest compatibility.
5. Compute planar X/Z distance from the character's verified final HRS landing
   position to each legal trader.
6. Select the shortest distance deterministically.
7. Resolve equal distances with a stable current-world identifier/coordinate
   ordering. Never reroll.
8. Change only the active objective destination to the chosen trader.

The implementation must use native registry and quest APIs. Do not scan or
rewrite world files, prefab files, save files, or vanilla XML.

## Quest invariants

Routing may alter only the destination of the exact opening trader objective.
It must not change:

- quest ID, phase, state, completion, or failure state;
- `StarterQuest` or unrelated CVars;
- stone shovel quantity or quality;
- the native `500 XP` reward;
- challenge rewards or skill points;
- trader tier, reputation, inventory, hours, protection, or faction;
- later jobs, trader-to-trader quests, or ordinary nearest-job selection;
- player position, biome protection, inventory, equipment, or world state.

## Persistence and exactly-once state

Use the per-character mod-owned CVar:

`bitwrecked_hrs_starter_trader_route_v1`

Proposed values:

- absent: no routing attempt;
- `1`: Pending — eligible placement completed, quest event not yet consumed;
- `2`: Reserved — exact quest event claimed and selection attempted;
- `3`: Completed — destination update verified;
- `4`: Invalid — malformed or contradictory state; grant no authority.

Reservation occurs before selection. A Reserved attempt is consumed even if no
legal trader is found, preventing reload/crash rerolls. Never reset or re-add
the native quest to force a second attempt.

## Failure behavior

On missing authority, unsupported game build, stale position, missing quest,
no legal trader, selector exception, destination-write failure, verification
failure, or ambiguous state:

- keep the native quest destination unchanged;
- do not modify quest state or rewards;
- do not move the player;
- do not retry with a different trader;
- emit only bounded sanitized diagnostics;
- preserve a recoverable prior build before live staging.
