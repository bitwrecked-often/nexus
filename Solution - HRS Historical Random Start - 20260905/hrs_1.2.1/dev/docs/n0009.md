## Security Workstream

Apply Linux-style operational hardening as an engineering standard without
claiming formal compliance. The helper is a small privileged runtime component,
so its default posture is least authority and fail closed.

Required controls:

- server-side authority and no Developer Mode or console commands;
- no runtime shell, network, registry, service, scheduled-task, or unrelated
  file activity;
- allowlisted and range-checked configuration;
- bounded candidate attempts, terrain work, waits, logging, and total runtime;
- explicit idempotent relocation states;
- defense-in-depth destination and protection validation;
- sanitized audit evidence with no secrets or private player identity data;
- package manifests and hashes; and
- tested rollback and fallback behavior.

Threat cases are first-class test cases: duplicate events, rerolls,
disconnects, malformed configuration, unbounded search, bad terrain,
client/server disagreement, exception paths, and protection that fails to
expire.

## Product Shape

exact new-game name and the two Standard/Random choices. Random invokes the
native-authored-spawnpoint atomic relocation once for a genuinely new player;

Treat the deployed solution as one manifest-owned capsule. Installation,

but are never owned or removed by this solution.

## Launcher and Session Workflow

### World index and status

- Store policy in a small external index keyed by world/game name.
- Default to the five most recently modified saves.
- Offer browse-for-one and load-all actions.
- Show `World`, `Status`, and `Spawn Policy`.
- New worlds begin `BYPASSED — vanilla spawn` in red.
- Active custom worlds show `ACTIVE — custom spawn policy` in green.

- While the game is running, show the current state read-only and disable the
  launcher’s own policy changes. Do not create pending saves.

### Target scope and fixed new-player trigger — owner decision 2026-08-21

Do not conflate **which games a policy covers** with **when the runtime may
act**. Target scope is player/administrator agency. The lifecycle trigger is a
fixed safety invariant.

The planned target-scope choices are:

1. `ExactNewGameName` — arm one not-yet-created game by an exact name typed in
   the launcher;
2. `DiscoveredGame` — select one game/save identity found by the read-only
   world index; and
3. `AllGames` — apply the chosen start policy across every otherwise eligible
   game in the configured local/server scope.

All three scopes retain the same non-configurable runtime trigger:

> Act only for a genuinely new player's first eligible arrival, at most once
> for that player in that game.

`AllGames` therefore does **not** mean “move a player whenever a game loads.”
Established players are never moved on ordinary load, reconnect, death,
respawn, or continued play. Eligibility still requires the approved lifecycle
reason, compatible build/runtime lane, authoritative context, valid policy,
and an absent per-player reservation/completion marker. Reservation precedes
selection, and a consumed attempt never rerolls.

For the first local single-player bridge, implement only
`ExactNewGameName`. The launcher presents a New Game option with a required
exact-name field and a Copy Name action. It rejects blank values,
leading/trailing whitespace, ambiguous normalization, and collisions with an
already discovered game. The runtime compares the game-reported name to the
saved canonical value exactly and fails closed on mismatch. After the game is
created, a rescan converts the provisional named target into an ordinary
discovered-game entry with its observed result.

The existing-game list remains valuable for discovery, status, policy history,
and future server use. In the initial single-player lane, an already completed
save is not offered another relocation. `DiscoveredGame` mutation and
`AllGames` remain planned scopes until their own state, authority, concurrency,
and multiplayer tests pass. UI fixtures may render them only when clearly
marked unavailable; they must not imply runtime support.

Keep target scope separate from start policy:

- target scope answers **where** the policy applies;
- `Standard` or `Random` answers **what** policy applies; and
- the fixed first-arrival gate answers **when and to whom** runtime work is
  permitted.

### Canonical Policy Eligibility Grid

This is the single authoritative decision grid for the launcher/runtime
bridge. UI capability predicates, policy-schema fixtures, runtime guards,
negative tests, support wording, and later implementation packets must cite
these row IDs. Other documents may summarize or reference the grid but must not
maintain competing copies.

Evidence labels mean:

- `OBSERVED` — exercised against the game in the exact private lane;
- `PURE` — proven only in source/static/model fixtures;
- `PLANNED` — accepted design without an enabled implementation; and
- `PENDING` — an implemented or observed claim still needs its named follow-up.

Denial gates are evaluated before permission rows: environment and policy
validity, target-scope match, new-player lifecycle, and marker state must all
pass before Standard/Random behavior is considered.

Grid invariants:

1. No row authorizes relocation for an established player.
2. No scope can override lifecycle, marker, compatibility, or authority gates.
3. Standard never calls the selector or placement path.
4. Random permits one candidate and one placement attempt, never a reroll.
5. `AllGames` changes only target coverage; it does not change trigger timing
   or per-player exactly-once semantics.
6. A UI selection is intent, not runtime permission. Runtime revalidates every
   controlling fact.
7. Any proposed behavior without a matching grid row is unauthorized until the
   owner approves a grid amendment and its tests.
8. EAC state is never changed by the AI, launcher, installer, or runtime. Lack
   of a positive approved-lane signal is denial, not evidence of compatibility.

### Policy modes

- `Standard` (internal `Vanilla`) is an exact no-op and uses the existing game
  method.
- `Random` uses the existing world spawnpoint list. Broader-coordinate or
  rooftop placement may be added later only as gated Random features, never as
  another mode.
- Random offers two default-off, mutually exclusive safeguards in one aligned
  row: `Starting biome only` and `All dangerous biomes`. They remain visible
  and editable under Standard so a player can prepare a preference, but
  Standard grants it no runtime authority.
- Starting-biome-only resolves no family or exactly the authoritative landing
  biome's reviewed hazard/storm family; all-dangerous-biomes resolves all four
  reviewed families. Relief is per Random-start character, is not broad damage
  immunity, and never edits biome XML.

## Alpha Recovery and Complete Local History — Owner Decision 2026-08-21

- Record every install, update, Apply, blocked, failed, cancelled, reset,

choosing a coordinate. The safety validator remains mandatory at every radius.

## Acceptance Criteria

### Core vertical-slice completion gate

The first product increment is complete when all of these are evidenced in the
pinned local single-player lane:

- the player manually enters one exact not-yet-created game name;
- blank, padded, ambiguous, malformed, incompatible, stale, and mismatched
  policies fail closed without selection or placement;
- the player chooses exactly Standard or Random and confirms the bounded saved
  policy before launch;
- the runtime validates the same versioned schema and exact target independently;
- only a genuinely new player's first eligible arrival can reach a policy action;
- Standard performs zero candidate selection and zero placement;
- Random invokes the proven native-authored-spawnpoint atomic state machine
  with exactly one candidate and no reroll;
- Absent, Reserved, Completed, and Invalid marker states have deterministic,
  tested outcomes;
- Completed persists across normal exit and reload and prevents a second
  selection or placement;
- reconnect, death, respawn, duplicate callback, launcher restart, and ordinary
  continued play cannot retrigger Random;
- a bounded sanitized result identifies bypass, completion, consumed failure,
  rejection, or incompatibility without raw identity or machine paths;
- launcher intent, saved policy, runtime decision, marker transition, placement
  result, reload result, and rollback are linked in one evidence packet;
- removing/disabling only the owned helper restores ordinary spawning for new
  tests without altering unrelated game content; and
- current-truth, build, test, recovery, and continuation documents agree.

Trader routing, biome safeguards, save discovery, broader scopes, multiplayer,
expanded coordinates, drops, protection, rooftops, packaging, and publication

- the chosen distance responds visibly to the slider;
- no hard safety rule is bypassed at `100%`;

- malformed or hostile configuration fails safely;
- repeated invalid candidates remain bounded in time and resource use;
- no runtime side effects occur outside the approved helper state/evidence

- the staged release contents and hashes match the approved manifest.

- saved settings are local to the Downloads copy and are not Git operations;

## Stop Conditions

The implementation AI must diagnose, revise, and retest ordinary engineering
failures rather than treating them as stopping conditions. A rejected input or
unsafe candidate must produce the defined fail-closed result and allow the
test campaign to continue.

Pause and request the exact missing human/external action only if:

- a person must authenticate, operate the game UI, or visually confirm runtime
  behavior that cannot be captured safely by the harness;
- the approved target, backup, recovery artifact, or rollback boundary cannot
  be verified;
- the next test would modify an unapproved game, save, world, XML, Harmony, or
  unrelated mod path;
- the installed game/API differs materially from the pinned evidence;
- completion requires a new public dependency, external upload/publication,
  credential, or private-data exposure; or
- two governing product requirements are mutually incompatible.

If the hook, terrain query, schema, marker, placement, or result channel fails,
keep the feature disabled, preserve vanilla behavior, record the evidence, and
continue investigating within the approved staged paths. If no safe design can
satisfy the core after alternatives are exhausted, return a precise NO-GO
finding rather than silently broadening authority or substituting a weaker
mechanic.

## Human Demarcation and Durable Handoff Protocol

The owner is the demarcation between agent-controlled engineering and
human-controlled live game operation. A pause for the owner is a typed workflow
state, not an informal chat interruption and not permission for the AI to infer
the result.

Before every human-operated game step, the AI must commit a project-local
handoff checkpoint containing:

1. a unique step and attempt ID;
2. the governing `PEG-*` case or acceptance criterion;
3. the exact game build, world, game name, policy revision, source/build/payload
   hashes, and expected owned Mod path;
4. confirmation that backup, rollback, logs, and pre-test baselines exist;
5. the exact human action in plain language, one action sequence at a time;
6. what the user should see and the bounded categories they may report;
7. visible and technical abort conditions;
8. what the AI will inspect after the human returns; and
9. the last safe resumable state if the session or machine stops.

The approval request must show the concrete action and target. "Continue?" is
not sufficient. Approval of one identified game launch, copy, reload, or
observation does not authorize later actions, other targets, publication, or a
broader path.

The user response is evidence input, not a substitute for technical evidence.
The AI must record it as one of `observed-as-expected`, `observed-different`,
`aborted`, or `not-observed`, then correlate it with the named log, marker,
hash, and filesystem checks. It must never convert silence, ambiguity, a stale
response, or session resumption into approval or a PASS.

After the user response and technical correlation, the AI writes a post-step
checkpoint before continuing. If the workflow resumes after interruption, it
must re-emit the pending human request with the same attempt ID and current
artifact identities; it must not execute the step again automatically.

Human approval is an execution-suspension response, not the source of project
authority. Authority still comes from this manifest, the READY execution
packet, the named paths, and the specific owner instruction. Identity and
scope must be verified independently before an approved action runs.

Autonomous engineering loops between human steps must be bounded by both:

- a semantic completion condition, such as all named tests passing with the
  required evidence; and
- an explicit attempt ceiling in the active execution packet.

Reaching the ceiling triggers a structured diagnosis/replan checkpoint, not a
scope expansion or weaker acceptance rule. The AI may continue after the
replan if it remains within existing authority and the revised approach is
recorded; otherwise it requests the exact missing decision.

This protocol is consistent with Microsoft Agent Framework guidance on
human-approved tools, request/response pauses, durable checkpoints, resumable
pending requests, and bounded agent loops. Microsoft guidance also treats
checkpoint storage as a trust boundary; therefore project checkpoints must be
local, bounded, integrity-checked where practical, and never rehydrated from an
untrusted recovery packet.
