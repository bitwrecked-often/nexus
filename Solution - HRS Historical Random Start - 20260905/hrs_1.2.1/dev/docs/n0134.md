# Historical Random Start — Pre-Test Bidirectional Drift Check Manifest

Date: 2026-08-27
Status: READY FOR READ-ONLY DRIFT CHECK
Authority: Drift discovery and reporting only
Active lane: `bit_wrecked_historical_random_start_0.0.5-alpha-tech-demo_2026-08-26`
Frozen reference: `bit_wrecked_historical_random_start_0.0.1-alpha_nexus-review_2026-08-26`

## 1. Objective

Determine, without changing or running the mod, where Historical Random Start's
current documentation, implementation, historical test evidence, generated
artifacts, frozen reference, Nexus copy, and transport expectations agree or
drift from one another.

The check is deliberately bidirectional:

1. documentation and handoff claims must be traced forward into source,
   artifacts, and evidence; and
2. implemented behavior and required operator actions must be traced backward
   into the documents that are supposed to teach them.

The output must identify proposed future corrections, but must not apply them.

## 2. Order of Work

The project must proceed in this order:

1. **Read-only bidirectional drift check** under this manifest.
2. **Separate owner-observed mod test** under a later, explicitly approved test
   manifest.
3. **Transport/repository hardening** based on the observed test result and
   accepted drift report.

Passing this drift check does not authorize the mod test. Passing the later mod
test does not automatically authorize documentation, source, packaging, Git,
Nexus, or transport changes.

## 3. Known Operator Sequence to Verify, Not Rewrite

Treat the following as the current candidate known-good sequence. Verify every
step against manager source, runtime source, and historical evidence. Report
any disagreement instead of silently reconciling it.

1. Start the functional Historical Random Start manager while the game is
   closed.
2. Enter the exact name intended for a not-yet-created New Game.
3. Select `Standard` or `Random`.
4. Select `Apply` and confirm the exact-name policy.
5. Apply validates prerequisites, creates or verifies the owned deployment
   boundary, builds/installs the runtime when required, and writes the bounded
   local policy.
6. The local person launches the normal non-EAC game lane, either through the
   manager's direct-user `Launch Game` action or an independently valid manual
   launch.
7. In 7 Days to Die, the person selects **New Game**, not a stale Continue
   entry, and creates the game with the exact armed name.
8. The runtime reads and caches the policy, validates build, EAC state,
   locality, single-player authority, exact game name, `NewGame` lifecycle, and
   marker state.
9. `Standard` records a categorical bypass and performs no selection or
   placement.
10. `Random` reserves the marker, requests one candidate from the native
    authored spawnpoint list, performs the deferred native placement, verifies
    the result, and marks the player/game completed.
11. Later loads, reconnects, deaths, respawns, duplicate callbacks, launcher
    restarts, and continued play must not cause another selection or placement.

The drift report must distinguish:

- behavior present in current source;
- behavior demonstrated by historical private testing;
- behavior not yet reconfirmed on this workstation/current installed payload;
  and
- roadmap behavior that remains disconnected.

## 6. Required Bidirectional Checks

### A. Front-door and operator-flow drift

Trace every human entry file and instruction to its actual target. At minimum,
check:

- the undated BAT;
- the dated `2026-08-21` BAT;
- the preview PowerShell tool;
- the functional manager PowerShell tool;
- `n0209.md` and `t0210.txt`;
- `n0152.md`;
- `n0150.md`;
- the current `0.0.5` start-here document; and
- the original product manifest and successful Phase 1A evidence.

Report which entry opens the preview, which opens the functional manager, any
stale version/comment text, and whether a transported user or AI is directed to
the correct sequence.

### B. Claim-to-code drift

For each operator-sequence claim, identify the implementing function, event,
branch, or contract. Verify at least:

- Apply is blocked while the game is running;
- exact-name validation occurs before policy write;
- build/deployment behavior when the owned bridge is absent;
- behavior when the owned bridge already exists;
- confirmation occurs before policy write;
- launch remains a direct-user action;
- runtime policy read/caching order;
- non-EAC, local-player, local single-player, server-authority, exact-name, and
  lifecycle gates;
- Standard no-op placement behavior;
- native spawnpoint selection;
- marker reservation/completion ordering;
- deferred placement and post-placement verification; and
- loaded-game/no-repeat behavior.

Do not infer successful live behavior solely from source presence.

### C. Code-to-document drift

Starting from the functional manager and release runtime, identify every action
that a transported user must know. Verify that current front doors explain:

- which BAT is functional;
- that the target New Game must not yet exist for the current exact-name scope;
- that Apply occurs before game launch and New Game creation;
- that the same name must be entered in both places;
- that Continue is not the first-run path;
- the non-EAC requirement;
- what Apply may build, install, and write;
- what Standard and Random do;
- the exactly-once/no-repeat boundary; and
- how status/result information is observed.

Missing, buried, contradictory, historical, or preview-only explanations are
drift findings.

### D. Evidence-to-current-claim drift

Separate these proof classes:

1. pure/static/contract-tested;
2. historically built and inspected;
3. historically observed in the private Phase 1/Phase 1A lane;
4. historically observed only for a probe rather than the release runtime;
5. present in current `0.0.5` source but not rebuilt/retested live as `0.0.5`;
6. pending current-workstation confirmation; and
7. planned/deferred only.

The successful exact-New-Game relocation evidence must be distinguished from
earlier failed or incomplete iterations. Do not let an older `NO-GO` statement
override later evidence, and do not let one later success erase unresolved
persistence or replication limits.

### E. Version and artifact drift

Inventory and compare:

- manager-visible version;
- release `ModInfo.xml` version;
- release-source manifest version and hashes;
- retained `out` and `tmp` identities;
- historical probe metadata;
- active/frozen file differences;
- root Git tracked versus ignored files; and
- Nexus Historical Random Start subtree contents.

Explicitly state whether an artifact is current source, historical evidence,
rebuildable output, a transport input, or a machine-local/runtime product.

### F. Transport-boundary drift

Classify every required part of a successful fresh-computer re-entry as one of:

- portable source/documentation;
- generated but reproducible;
- required game-provided dependency;
- intentionally machine-local policy/runtime state;
- private evidence that must not ship;
- release payload candidate; or
- forbidden credential/private material.

Identify what a source-only copy, ordinary Git checkout, full solution-capsule
copy, and player release package would each contain or omit. Do not build or
copy anything during this check.

### G. Frozen and external-reference integrity

Reconfirm with read-only hashes that:

- the frozen lane has not changed;
- the local Nexus Historical Random Start subtree has not changed;
- their intended comparison roots are correctly aligned; and
- no proposed correction is applied to either reference.

## 8. Acceptance Criteria

The drift check passes when:

- the current functional entry and preview entry are unambiguously identified;
- the candidate operator sequence is verified step by step against source;
- every material handoff claim is classified by proof level;
- contradictions and stale statements are reported without being edited;
- the current and historical artifact/version boundaries are explicit;
- the fresh-computer loss-of-context mechanism is explained from evidence;
- frozen and Nexus references remain unchanged;
- no game, build, install, policy, save, live payload, Git, or external action
  occurred; and
- the report leaves a clear owner checkpoint before any live test.

## 9. Stop Conditions

Stop and report without widening scope if:

- resolving a finding requires launching or modifying the game;
- the installed payload or policy must be read to settle the question;
- a save, raw log, credential, key, or private record would need inspection;
- frozen or Nexus hashes disagree;
- the active lane contains unexplained source changes;
- a supposedly read-only command would create external state; or
- documentation and implementation disagree about an action that could affect
  a live game, save, world, or unrelated mod.

## 10. Required Handoff

Return the drift report to the owner for review. The owner decides whether the
reported current operator sequence is accepted as the test candidate.

Only after that approval may a separate manifest define the smallest safe live
test. Only after the test result is accepted may another separate manifest
authorize transport/repository hardening.
