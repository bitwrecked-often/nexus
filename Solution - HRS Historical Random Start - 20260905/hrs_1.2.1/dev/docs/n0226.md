# Historical Random Start - Alpha 6 Method — UX-0/UX-1 Control and State Model

Date: 2026-08-14
Status: Pure design contract; no functional launcher behavior enabled
Evidence basis: `evidence/n0012.md` and
`n0227.md`

## Purpose

This document converts the Day 2 visual review into a control inventory and a
pure state/capability model. It preserves the Bit Wrecked family resemblance
while removing controls that currently imply capabilities the project does not
own.

The model is deliberately render-first and side-effect-free. A renderer may
show a capability only when the current state owns that capability. No action
in this document authorizes policy writes, game launch, installation, removal,
or gameplay runtime code.

## UX-0 control inventory

Disposition terms:

- `Retain` — keep the role, subject to hardening and truthful wording.
- `Replace` — preserve the visual area but change the product-specific action.
- `Add` — required by the approved workflow.
- `Remove` — inherited or speculative capability with no approved owner.
- `Gate` — may be rendered as disabled/explanatory only until its prerequisite
  is proven.

| Current or target control | Disposition | Owner/capability | Required truth |
| --- | --- | --- | --- |
| Bit Wrecked identity/header | Retain | Host identity | Branding does not imply runtime readiness |
| Status card | Replace wording | Host status read | State names must describe folder/save/runtime truth separately |
| Game-folder row / Choose Game Folder | Retain | Read-only root discovery | Recognized folder is not an installed or compatible runtime |
| `Validate Current Game Settings` | Replace | Explicit validation reads | The label must say whether it reads root, saves, policy, runtime, or launch readiness |
| Five recent save instances | Add | Save discovery and selection | Show stable world/game identity without player identity or raw private paths |
| `Browse for Another World` | Add | One-save discovery | Browse one valid save; do not silently load all saves |
| `Load All Worlds` | Add | Explicit full enumeration | Keep UI responsive and preserve stable selection |
| `World` / `Status` / `Spawn Policy` columns | Add | Read-only world index | A new world is visibly `BYPASSED — vanilla spawn` until explicitly saved active |
| ACTIVE/BYPASSED text state | Add | Policy state read | Text carries meaning; color only reinforces it |
| Standard / Random choices | Replace placeholder | In-memory policy edit | These are the only start types; values do nothing until a reviewed save workflow exists |
| Nearest opening trader guidance | Add informational copy | Derived core behavior for Random | No checkbox; Standard is untouched and runtime remains gated |
| Random Distance | Gate | Future expanded-Random policy field | Hidden or disabled for Standard and unavailable before the experimental gate |
| Starting biome only checkbox | Add; unchecked by default and always editable | Random safeguard enum `ArrivalBiome` | Resolves only the authoritative landing biome's reviewed family; every other dangerous biome remains active; ignored by Standard |
| All dangerous biomes checkbox | Add; unchecked by default and always editable | Random safeguard enum `AllDangerousBiomes` | Resolves all four reviewed families; checking it clears starting-biome-only; ignored by Standard |
| Running-game indicator | Add | Read-only lock | Disable launcher mutation and policy launch controls; leave viewing available |
| Saved Settings Record | Add | Save-result detail | Show world, previous/new policy, UTC time, launcher version, result |
| `Save Settings` | Gate | Confirmed atomic persistence | Disabled until Phase 0A contract and prerequisites are approved |
| `Launch Game` | Add; always visible | Direct local-user handoff only | Requires Steam; only the person who opened the manager may click it; AI/automation cannot activate it; incomplete configuration launches with this mod inactive |
| Launch readiness message | Add above controls | Read-only status | Show `Configuration incomplete — mod not enabled` when applicable; never place status copy inside the button |
| Non-EAC requirement/status | Add | Read-only instruction and runtime capability result | Before launch say `Required — choose Launch without EAC`; after evidence show only `Confirmed` or `Runtime lane unconfirmed`; never offer a disable/fix button |
| Capsule conflict state | Add | Install/update ownership gate | Show `Existing installation requires review`; keep Launch Game available, keep this mod inactive, and provide bounded details without altering Harmony or unrelated mods |
| `Runtime Not Built` | Remove from functional build | None | A design-shell truth label is not a user action |
| `Remove from Game` | Add under Details; available when game closed | Deployed-capsule removal | Confirm, remove only verified solution-owned game artifacts, retain portable manager/history, and never touch system/shared/other-solution content |
| `Recovery` | Add | Local validated recovery | Default plus five latest attempts; failed/unavailable attempts remain visible but cannot be restored |
| `Show Changes` | Add; read-only | Current/previous comparison | Plain-language bounded diff correlated to history/log note |
| `Open Mods Folder` | Remove initially | None | Unrelated folder access is not part of the first workflow |
| `Close` | Retain | Local desktop behavior | Closing discards only in-memory edits and creates no pending file |
| Layered Reasoning Log / Recent Actions | Retain and harden | Bounded session evidence | Do not log raw policy, private identity, or unrelated paths |
| Persistent log controls | Retain and harden | Explicit consent/path capability | Off by default; no silent file creation; disabling never deletes |
| Generic `Feature Group | Control | Action | Current | Result` headings | Remove | None | They are inherited template language, not this product's workflow |
| Reserved world-policy checkbox | Remove | None | A disabled placeholder must not imply a hidden feature |

## Target information model

The first functional surface should read in this order:

```text
Identity and truthful readiness status
Game folder                                      [Choose Game Folder]
Recent world saves: World | Status | Spawn Policy
      [Browse for Another World] [Load All Worlds]
Selected-world policy: ACTIVE/BYPASSED
      Standard | Random
      Random opening trader -> nearest valid trader
      Future Random distance and two default-off, mutually exclusive safeguards
Saved state versus in-memory edit explanation
      [Apply] [Launch Game] [Close]
      Configuration incomplete — mod not enabled (when applicable)
      Non-EAC status: Required / Confirmed / Runtime lane unconfirmed
      [Recovery] [Details: capsule inventory, history, Remove from Game]
Layered Reasoning Log / Recent Actions
```

This is an information architecture, not a pixel requirement. A list view,
split detail pane, radio group, or another native control set is acceptable if
it preserves the same semantics, keyboard order, accessibility names, and
state gating.

## Pure state model

The UI model contains no file handles, processes, controls, callbacks, or
side-effecting delegates. It can be serialized as a test fixture but is not
itself the persisted policy.

```text
GameRootState =
  Unrecognized
  | Recognized { rootFingerprint }

SaveDiscovery =
  NotRun
  | NoSaves
  | Recent { rows, totalCount }
  | All { rows, totalCount }
  | Failed { reasonCode }

TargetSelection =
  None
  | Discovered { saveRecord }
  | ProposedNewGame { exactGameName }

TargetScope =
  ExactNewGameName
  | DiscoveredGame
  | AllGames

EditState =
  NoEdit
  | InMemory { policy, baselinePolicy, validation }

RuntimeObservation =
  Unknown
  | Closed
  | Running
  | IdentityUnavailable

PolicyValidity =
  Missing
  | Valid { policy }
  | Invalid { reasonCode }
  | MismatchedWorld { reasonCode }

ModelState = {
  gameRoot, discovery, targetSelection, targetScope, edit, savedPolicy,
  runtimeObservation, runtimeCompatibility, logCapability,
  lastSavedSettingsRecord, pendingValidation
}
```

`TargetScope` controls which games are covered; it never controls lifecycle.
Every scope retains the fixed eligibility rule: a genuinely new player's first
eligible arrival, at most once per player/game. The first implementation
permits only `ExactNewGameName`. `DiscoveredGame` mutation and `AllGames` remain
model values for fixtures until their separate gates pass.

Expected actions and outcomes come from the `Canonical Policy Eligibility
Grid` in `n0009.md`. Pure fixtures should
carry the applicable `PEG-*` row ID so state-model tests remain traceable to
the single planning authority.

`pendingValidation` carries a monotonically increasing request token and the
input fingerprint. A result is applied only when both match the current model;
otherwise it becomes a stale-result event and cannot change visible state.

## Capability predicates

Capabilities are derived values. They do not grant authority by themselves.

| Capability | Predicate | Forbidden implication |
| --- | --- | --- |
| `CanChooseGameFolder` | Not running; no write is required to inspect a candidate root | Does not mean the root is valid |
| `CanDiscoverSaves` | Root is recognized and no conflicting discovery is active | Does not authorize policy mutation |
| `CanSelectSave` | Discovery has a valid row and the row is not stale | Does not load private player data |
| `CanBrowseOne` | Root is recognized and launcher is not running-locked | Does not replace the five-recent default |
| `CanLoadAll` | Root is recognized and launcher is not running-locked | Does not allow unbounded blocking enumeration |
| `CanPrepareExactNewGame` | Root recognized, runtime closed, exact name nonblank/canonical/collision-free, no validation conflict | Does not assert that the save already exists |
| `CanEditPolicy` | Valid discovered target or valid proposed exact-name target, runtime closed, no validation conflict | Edit is in memory only |
| `CanUseAllGames` | Separate server/multiplayer authority, concurrency, reconnect, per-player isolation, and clean-client gates all pass | Never moves an established player or reruns on load/respawn |
| `CanUseExpandedRandomControls` | Selected edit is Random and the experimental extension is explicitly enabled by a later gate | Never creates another mode or affects Standard |
| `CanUseRandomSafeguards` | Selected edit is Random, Phase 1C is approved, and scope is exactly `None`, `ArrivalBiome`, or `AllDangerousBiomes` | A checked scope is not a compatibility or immunity claim |
| `CanValidatePolicy` | Selected policy exists in memory or saved state | Validation is read-only |
| `CanSaveSettings` | Closed, selected, valid policy, owner confirmation, approved persistence contract, verified destination | No save before Phase 0A approval |
| `CanLaunchGame` | Steam running and direct local-user activation | Never implies mod readiness; AI, timers, automation, and other controls cannot activate it |
| `CanViewState` | Any model state | View access remains available while running |
| `CanMutatePolicy` | `CanEditPolicy` and runtime observation is exactly `Closed` | Unknown process identity fails closed |
| `CanRestore` | Game exactly closed and selected target passes immediate revalidation | Never queues a change; failed/unavailable history is not a restore target |
| `CanRemoveFromGame` | Game exactly closed and deployed ownership validates | Never removes manager/history, system files, shared dependencies, or unrelated mods |
| `CanPersistentLog` | Explicit consent, valid local path, bounded writer available | No silent log file creation |
| `CanRunRuntimeRelocation` | Server authority, valid active non-Vanilla policy, new-character proof, marker `Absent`, runtime gate accepted | UI selection alone cannot trigger it |
| `CanRetargetStarterTrader` | Completed authorized Random placement, route marker `Pending`, exact active starter quest/phase/objective, authoritative native event, compatible current API | Never resets/completes a quest or affects Standard/other quests |

The renderer must use the same predicates as action dispatch. A button that is
visible but not actionable must state the missing prerequisite, not look like a
working feature.

## State transitions

| From | Event | Guard | Result |
| --- | --- | --- | --- |
| Any | Choose folder | Folder read is bounded and read-only | Recognized or Unrecognized |
| Recognized | Discover saves | Root fingerprint unchanged | NoSaves, Recent, All, or Failed |
| Recent/All | Select row | Row remains present and valid | Discovered target + saved policy resolution |
| Recognized | Enter proposed New Game name | Exact canonical value is valid and collision-free | ProposedNewGame target; no save identity is invented |
| Valid target | Choose policy | Game exactly Closed | InMemory edit; no write |
| InMemory | Validate | Input token still current | Valid, Invalid, or MismatchedWorld |
| InMemory | Save request | All `CanSaveSettings` guards and explicit confirmation pass | Atomic saved result or SaveFailed |
| Saved | Game starts | Process identity is rechecked | RunningReadOnly or launch blocked |
| Any | Game running/identity lost | Observation is Running or IdentityUnavailable | RunningReadOnly; discard no files and disable mutations |
| Any | Close | No external mutation | Exit; in-memory edit disappears |
| Any | Stale async result | Request/input token mismatch | Ignore result; log bounded stale-result code |

No transition from a dropdown change, folder recognition, log expansion, or
window close writes a policy. No transition from `RunningReadOnly` mutates
policy or creates a pending save.

## Explanation and History Contract

- The upper status area owns essential state, blockers, and next steps.
- Tooltips briefly explain the indicated control's outcome in plain language.
  They are not warnings, manuals, or repetitions of the control label.
- Do not mimic another platform's appearance. Apply broadly sound clarity,
  hierarchy, disclosure, and accessibility guidance to this Windows game tool
  and Bit Wrecked's visual language.
- Tooltip meaning must also reach keyboard and screen-reader users.
- Every event is local and matches user notes to diagnostic logs using one
  correlation ID. Failed attempts remain listed; only immediately revalidated
  known-good configurations enable Restore.
- Recovery always includes Default and retains the five newest attempts.
- Restore confirmation names association, before/after state, and save/world
  non-impact. A running game blocks Restore and every other mutation.

## Policy rendering rules

- `BYPASSED — vanilla spawn` is red in the current visual language, but the
  words remain readable without color.
- `ACTIVE — custom spawn policy` is green only for an approved active custom
  mode. `ACTIVE + Vanilla` needs owner-approved wording and must explain that
  gameplay is an exact no-op.
- Missing policy is displayed as bypassed/Vanilla in memory only. It is not
  written merely because a save was discovered.
- Random shows authored-spawnpoint explanations only after its
  runtime gate is accepted; before then they are design choices, not ready
  gameplay actions.
- `How It Works` explains that Random will route the stone-shovel starter quest
  to the nearest valid trader. Preview wording is not a runtime
  readiness claim.
- Random safeguard runtime capabilities are unavailable until the Phase 1C
  proof succeeds. Expanded-coordinate and rooftop Random capabilities require
  their later separate gates. Visible preferences do not imply readiness.
- The preview may show the two Random safeguard checkboxes before
  runtime approval only when it also says they are unsaved and unapplied to
  policy, game, and runtime. `Applied to this open session` may describe only
  an in-memory preview snapshot and must never be rendered as Saved Settings,
  persisted policy, or gameplay authority.
- A first unsaved preview initializes both scopes unchecked (`None`). The
  controls stay enabled under every start choice, are mutually exclusive, and
  a saved valid policy is rendered as saved rather than silently reset.
- The native whole-world `BiomeProgression` value is displayed as read-only
  compatibility context and is never silently changed by these controls.
- Leaving both safeguards unchecked shows complete vanilla hazard behavior.
  Starting-biome-only copy says all other dangerous biomes remain active;
  all-dangerous-biomes copy names the four reviewed families. Neither promises
  protection from enemies, falls, POIs, or ordinary damage.
- A selected policy is never displayed as active solely because a control is
  selected.

## Accessibility and responsive requirements

Every interactive or dynamic element needs a meaningful accessible name,
description, role, deterministic tab order, visible keyboard focus, and a
state change that is understandable without color. The test surface must
cover:

- 100% and 150% DPI;
- Windows High Contrast;
- keyboard-only selection, editing, save confirmation, popup action, log
  controls, and close;
- keyboard-only Random mode and both independently named, always-enabled,
  mutually exclusive safeguard checkboxes, including scope explanations;
- long world/game names without clipping or identity loss;
- five-row and all-world views;
- compact, expanded, resized, and maximized log layouts; and
- Narrator observation before any accessibility claim.

The expanded log must not consume the workspace to the point that the policy
task becomes unusable. The original 620-pixel partition is visual lineage, not
a fixed product requirement.

## UX-1 negative model cases

The pure model must return a safe state for each case:

1. Recognized folder with no saves: no policy controls imply readiness.
1a. Non-EAC not positively confirmed: Random is unavailable; no reservation,
    selection, or placement; no EAC-changing action is offered.
1b. Owned destination contains unknown/drifted files or identity collision:
    install/update is blocked, Launch Game remains available, Historical Random
    Start remains inactive, and no neighboring mod is changed.
2. Duplicate world/game names: selection remains instance-specific.
3. Unknown or mismatched policy version: display validation failure and keep
   the world bypassed/Vanilla in memory.
4. In-memory edit followed by close: no pending record exists.
5. Game starts while editing: transition to `RunningReadOnly`; edit cannot be
   saved or launched.
6. Process identity cannot be established: same fail-closed lock.
7. Validation returns after selection changes: stale result is discarded.
8. A stale future Random-distance value exists under Standard: that distance
   control is hidden/disabled and its stale value has no effect.
9. Persistent-log consent is cancelled: no file capability is granted.
10. Save verification fails: no success popup, no launch capability, no
    partial/pending policy.
11. First unsaved preview: both safeguard boxes initialize unchecked (`None`)
    in memory only; no record is written.
12. One safeguard is checked under Standard: both controls remain editable and
    retain the in-memory choice, while copy says Random only and runtime does
    zero safeguard work.
13. Selecting starting-biome-only and then all-dangerous-biomes, or the reverse:
    the newly selected scope clears the other; both can be cleared to `None`.
14. Switching between Standard and Random: the one selected scope remains
    stable; Standard still produces zero safeguard behavior.
15. Runtime lacks relief required by `ArrivalBiome` or
    `AllDangerousBiomes`: Random placement falls back before landing; no safety
    claim or hidden fallback to unsafe placement occurs.
16. Native `BiomeProgression` off/on: render the whole-world state truthfully,
    never write it from a safeguard-scope control, and perform no custom suppression
    when native hazards are already off.
17. Standard or existing character receives the starter quest: no custom
    destination or route-marker work occurs.
18. Random starter quest is accepted before Phase 1B compatibility
    is proven: keep the native destination and show no success claim.
19. An unrelated, duplicate, completed, or later trader quest event arrives:
    ignore it; no destination, reward, or state changes.

## Completion meaning

UX-0/UX-1 is complete for documentation review when the control inventory,
pure state model, capability predicates, transition rules, and negative cases
agree with the Phase 0A security baseline and UX manifest. This is not a
functional launcher milestone and does not permit writes, launch handoff,
installation, or runtime gameplay code.
