# Historical Random Start - Alpha 6 Method — Phase 0A Security and State Baseline

Date: 2026-08-14  
Status: Draft contract; documentation only; not implementation approval  
Scope: Launcher policy model, runtime-helper state, bounded side effects, and
pre-DLL negative-test requirements

## Purpose

This document turns the project manifest into a testable Phase 0A contract. It
defines the smallest permitted state and authority surface before any runtime
code is compiled or copied. It does not authorize a live `Mods` change, a
policy writer, a launch handoff, a save/world change, or a public package.

The core safety rule is:

> If identity, authority, configuration, destination, persistence, or runtime
> compatibility is uncertain, leave the ordinary game spawn untouched.

The core proof remains the native authored-spawnpoint, direct-grounded path.
Arbitrary-coordinate Random expansion, above-ground drop, arrival protection,
and distance agency remain separately gated experimental behavior.

## Authority and ownership

There are three separate authorities:

| Authority | Owns | Must not do |
| --- | --- | --- |
| Launcher | World selection, saved policy, user confirmation, local saved-settings record | Write game/world files, infer runtime readiness, or silently resolve the launcher-only handoff decision |
| Runtime helper | Read and validate the session policy, observe the spawn/quest lifecycle, perform the approved server-side relocation and exact starter-trader destination update, and record its own bounded state | Change launcher policy, use console/developer commands, alter rewards/quest state, or search without a bounded gate |
| Game/server | Character lifecycle, world state, authored spawnpoints, terrain truth, and final player authority | Be treated as safe merely because a launcher folder exists |

The runtime helper must operate on the authoritative server side when the
current API supports that distinction. A client-side observation or client
request is never sufficient authority for relocation.

## State model

### Launcher state

The launcher keeps an in-memory view and a separately persisted saved policy.
There is no on-disk pending-settings state.

| State | Meaning | Safe actions |
| --- | --- | --- |
| `NoGameRoot` | The selected folder is absent or not recognized | Choose folder, view log, close |
| `GameRootReadyNoSaves` | The folder is valid but no readable save instance was found | Browse/refresh if available, view log, close |
| `SavesReadyNoSelection` | Save instances exist but none is selected | Select, browse one, load all, view log |
| `SelectedUnsaved` | A save is selected and edits exist only in memory | Validate, discard, confirm/save while closed |
| `SavedBypassed` | The selected world has a verified bypassed/Vanilla policy | View, edit while closed, launch only if a separate approved handoff exists |
| `SavedActive` | The selected world has a verified active policy | View, edit while closed, launch only if runtime and handoff gates pass |
| `RunningReadOnly` | Game process state is running or cannot be safely distinguished from running | View saved state and log only |
| `ValidationBlocked` | A read or policy check failed or returned stale data | Read the reason, correct through a reviewed flow, remain safe |
| `SaveFailed` | An explicit save did not complete and was not verified | Retry after correction; never show success |

`ACTIVE + Vanilla` remains an owner decision. The model may carry
`activation=Active` and `mode=Vanilla`, but rendering and release wording must
not claim that Vanilla performs custom relocation. Until the wording is
approved, the UI must use an explanatory no-op sentence and must not silently
normalize the state.

### Runtime state

The runtime state is per world/session and is intentionally narrower than the
launcher state:

```text
Unavailable
  -> SessionObserved
  -> PolicyValidated
  -> AwaitingFirstSpawn
  -> SpawnObserved
  -> ReservationWritten
  -> CandidateValidated
  -> PlacementVerified
  -> CompletionWritten
```

Any state may enter `VanillaFallback` when a required precondition fails. A
`ReservationWritten` marker is treated as consumed on recovery; it prevents a
crash between reservation and completion from creating a second relocation.
`PlacementVerified` without a successful completion write is not permission
to retry. It is a recovery failure that falls back to ordinary behavior on a
later lifecycle event.

The runtime must reject or ignore these events for the first proof:

- ordinary login or reconnect;
- death and ordinary respawn;
- duplicate delivery of the same spawn event;
- a player that already has a consumed or reserved marker;
- a non-authoritative client-side event; and
- a policy that is missing, malformed, mismatched, or not explicitly active.

Starter-trader continuity is a separate Phase 1B substate after placement:

```text
Absent
  -> Pending
  -> Reserved
  -> Completed
```

`Pending` waits for only the exact native starter-quest event and performs no
polling. `Reserved` consumes the sole route attempt before selection. Any
failure after reservation remains consumed and leaves the native destination
untouched; it never retries on another callback or lifecycle event.

### Marker contract

Exactly-once behavior requires a stable game-owned character/player record or
another API-proven per-world marker. The helper must not invent a raw platform
identity store. Steam IDs, account IDs, tokens, server addresses, and private
player data are forbidden in project state and logs.

If the current API cannot provide a stable non-sensitive marker, the runtime
must fail closed and the Phase 1A proof cannot pass. Hashing a forbidden
identity does not make it an approved identity source.

Marker values are limited to an allowlisted enum:

- `Absent` — no relocation reservation exists;
- `Reserved` — this new-character start is consumed and placement may not be retried;
- `Completed` — relocation was verified and recorded; and
- `Invalid` — state could not be parsed or does not match the current world/session.

`Invalid` is a fail-closed condition, not a request to repair by deleting the
marker.

Installed-build inspection on 2026-08-14 selected the game-owned player CVar
route as the only Phase 1A marker candidate:

`bitwrecked_hrs_state_v1`

Its numeric encoding is fixed to `Reserved=1.0`, `Completed=2.0`, and
`Invalid=3.0`; absence is checked with `EntityBuffs.HasCustomVar(...)`. The key
is nonzero, does not begin with `.`, and static inspection confirms that the
current `EntityBuffs.Write(...)`/`Read(...)` path serializes and restores that
class of CVar. The observation-only Phase 1 probe does not write it.

The core Random safeguard contract additionally proposes one bounded
per-character CVar, `bitwrecked_hrs_random_safeguard_mask_v1`, only after the
main marker is `Completed` and the Phase 1C gate is approved. It is an integer-
valued four-bit mask:

- bit `1` — Snow hazard relief;
- bit `2` — Burnt Forest hazard relief;
- bit `4` — Wasteland hazard relief; and
- bit `8` — Desert hazard relief.

Allowlisted values are exactly `1`, `2`, `4`, `8`, or `15`; absence means no
custom biome relief. The default-off two-checkbox policy produces no mask and
requires no zero-valued CVar write. `ArrivalBiome` is resolved by the server to
absence or exactly one family bit from the authoritative landing biome.
`AllDangerousBiomes` resolves to `15`. The launcher never supplies a mask, and
arbitrary family combinations are invalid. A visible choice under Standard or
Random grants no runtime authority by itself. This is a future design contract,
not an authorized runtime write. It may not identify a player, grant broad
damage immunity, or apply to a character that did not complete a Random start.

The core Random lane additionally proposes one bounded per-character CVar for
Phase 1B:

`bitwrecked_hrs_starter_trader_route_v1`

Its numeric encoding is `Pending=1.0`, `Reserved=2.0`, `Completed=3.0`, and
`Invalid=4.0`; absence means no starter-trader routing authority. `Pending` may
be written only after the main relocation marker is `Completed` for an
authorized Random start. `Reserved` is written before one nearest-
trader selection. Malformed, contradictory, already reserved, or completed
state is fail-closed and is never repaired by deletion.

This decides candidate API routes without claiming runtime durability. The
main relocation marker must pass in a disposable Phase 1A target; the starter-
trader marker must separately pass save timing, crash-window, reload,
reconnect, death, and server/client checks in Phase 1B. If either proof fails,
that marker is treated as unavailable and its custom action remains blocked.

## Policy and configuration bounds

The persisted policy is versioned, strict, and small. The initial shape is a
design contract, not a runtime schema implementation.

Required fields:

| Field | Bound and rule |
| --- | --- |
| `schemaVersion` | Exact supported version `1`; unknown versions are rejected |
| `worldRecord` | Launcher-created opaque record binding; no raw player identity |
| `activation` | `Bypassed` or `Active` only |
| `mode` | `Vanilla` or `Random` only; every legacy or third value is rejected |
| `randomDistancePercent` | Future integer `0..100`; meaningful only after the expanded-Random gate |
| `randomBiomeHazardReliefScope` | Exact enum `None`, `ArrivalBiome`, or `AllDangerousBiomes`; default `None`, editable under both displayed types, and ignored by runtime under Standard/Vanilla |
| `createdUtc` / `updatedUtc` | Valid UTC timestamps; no future-dated policy accepted beyond clock-skew tolerance |

The runtime revalidates every field independently of launcher validation. It
must reject duplicate fields, unknown required-shape fields, nulls where an
enum/value is required, oversized records, path-like values, coordinates,
commands, executable paths, and arbitrary JSON/script content.

Mode authority:

- `Bypassed` leaves vanilla spawning untouched.
- `Active + Vanilla` is an exact gameplay no-op.
- `Active + Random` may use only the native authored
  spawnpoint-list route after the Phase 1A gate.
- Every other mode value is invalid and fails closed without migration or
  inference.
- `ArrivalBiome` may resolve only the authoritative landing biome's reviewed
  family and requires that family to be approved and available when dangerous.
  `AllDangerousBiomes` requires all four reviewed families. Missing required
  compatibility falls back before placement.
- Biome relief may affect only the resolved one-family or all-four mask for the
  completed Random-start character. It cannot affect global XML, another
  player, ordinary damage, lootstage, gamestage, or unrelated buffs.
- The current native `BiomeProgression` game stat is a whole-world authority.
  The launcher/runtime may read and honor it but may not silently write it to
  implement a per-character safeguard scope. Native off means no custom
  suppression work; native on still requires the narrow Phase 1C gate.
- After Phase 1B, a completed authorized Random placement may update
  only active `quest_whiteRiverCitizen1` phase-one trader destination through
  the reviewed native event/objective path. Standard and all other quests do
  zero route work. No policy field or launcher checkbox controls this core
  continuity behavior.

No persisted field may directly name an X/Z destination. The helper chooses a
candidate only after the mode and safety gates permit it.

## Resource limits

These are conservative initial contract limits. They must be measured against
the target build before implementation and may be lowered after evidence; they
may not be silently raised to make a failing test pass.

| Resource | Initial limit | Failure behavior |
| --- | ---: | --- |
| Native core relocation selections | 1 | Vanilla fallback |
| Starter-trader route reservations | 1 per eligible character | Keep native quest destination; never retry |
| Native nearest-trader selections | 1 after route reservation | Keep native quest destination |
| Starter-quest destination mutations | 1 exact objective | Reject any other quest/phase/objective |
| Experimental expanded-Random candidates | 12 per new-character event | Vanilla fallback |
| Terrain probes | 1 per candidate | Reject candidate |
| Chunk-readiness waits | 4 total per event | Vanilla fallback |
| Wait per readiness check | 250 ms | Reject or fall back |
| Total runtime work | 5,000 ms per event | Stop and fall back |
| Arrival protection | 15 seconds absolute maximum | Clear protection and record failure |
| Visible activity entries | 128 per session | Drop oldest visible entry only |
| Visible entry size | 512 UTF-16 characters | Truncate with an explicit marker |
| Optional persistent log | 64 KiB per session | Stop writing; preserve gameplay safety |
| Policy record | 16 KiB | Reject as oversized |
| Saved-settings record | 8 KiB | Reject as oversized |
| Random safeguard scope | One exact enum / derived mask absent, one bit, or `15` | Reject unknown enum, launcher-provided mask, or invalid resolved value; no relief and no unsafe Random placement |

Limits apply on every event and cannot be reset by duplicate callbacks,
reconnects, malformed configuration, or a new candidate loop.

## Approved side effects

During the documentation and Phase 0A stage, approved side effects are zero.
The following is the future logical boundary for implementation and test
fixtures:

1. Launcher policy index and Saved Settings Record in the user-selected local
   Downloads copy owned by this project.
2. Runtime marker/state through the approved game-owned per-character CVar
   route, only after the target, save/rollback, and persistence gates are
   approved.
3. Optional persistent diagnostic log at an explicitly consented local path,
   subject to the hardened host path rules.
4. The authoritative game API call that performs the approved relocation.
5. After Phase 1B approval, one native destination/map-object update for active
   `quest_whiteRiverCitizen1` phase-one `trader`, plus its bounded game-owned
   per-character route marker. No quest completion/reward mutation is allowed.
6. After Phase 1C approval, the narrow game API calls that suppress and clean
   up only the resolved initial-biome family or all four reviewed current-build
   Random-start families for the eligible character.

Forbidden side effects include game XML, `Data/Config`, executables, core DLLs,
Harmony files, `serverconfig.xml`, saves/world files outside the approved
marker mechanism, registry, services, scheduled tasks, startup entries,
network, shell/console commands, downloads, telemetry, account access, and
unrelated file enumeration.

### Write protocol

Every future local write must use this protocol:

1. Resolve and canonicalize the approved destination.
2. Confirm the destination remains inside the allowlisted project-owned root.
3. Validate the complete bounded record before opening a file.
4. Write a uniquely named temporary file in the same directory.
5. Flush and close it, then verify size and parseability.
6. Atomically replace the target on the same volume.
7. Re-read and validate the committed target.
8. Remove only the specifically created temporary file after success or
   failure; never perform broad cleanup.

Failure at any stage produces no success state. The launcher has no pending
policy file to recover or apply later. A runtime reservation is consumed even
when its completion write fails, so a write failure cannot cause rerolling.

## Sanitized evidence log

Logging is evidence, not authority. Runtime logging is bounded and on by
default only in memory. Persistent logging is off until the owner explicitly
consents to a local path.

Allowed fields:

- UTC timestamp;
- component tag (`Host`, `Validation`, `Policy`, `Spawn`, `Placement`,
  `TraderRoute`, `Persistence`, `Lock`, or `Fallback`);
- event code from an allowlist;
- sanitized state before/after;
- mode and activation enum;
- bounded reason code;
- duration bucket or bounded integer milliseconds;
- candidate ordinal, attempt count, and resource-limit outcome; and
- coarse position/terrain result only when needed for a test, never a raw
  personal or private path.

Forbidden fields:

- Steam/account/player IDs, tokens, passwords, server addresses, or private
  identity details;
- raw policy JSON;
- raw command lines or executable arguments;
- full game/save paths or arbitrary filesystem listings;
- raw exception text containing paths or identity;
- network data or telemetry; and
- unbounded coordinates, candidate lists, or stack traces.

Every failure log must be safe to show to another person without disclosing
private machine or player information. Redaction is performed before the
record enters the visible log, not only during export.

## Required Phase 0A review inputs

Before the first DLL or functional policy writer, the project must have:

- a pinned target game/runtime fingerprint;
- an exact source/build recipe and dependency list/SBOM plan;
- the owned staged installation path and removal/rollback path;
- a marker API decision backed by installed-build evidence;
- a compatibility/EAC disclosure with no unsupported claim;
- scanner-friendly behavior and artifact hash plan;
- the negative-test matrix in `tests/` executed or explicitly marked pending;
- the owner decision about launcher-only Random activation before any
  launch handoff is designed; and
- a written go/no-go review for Phase 1 no-teleport event observation.

Until those inputs exist, the only permitted work is documentation, pure
models, fixtures, and read-only inspection of the current project boundary.

The candidate pre-build packet at
`n0191.md` now supplies the static
fingerprint, marker-route decision, source layout, build recipe, dependency
record, target schema, and passing pure fixtures. It does not supply an exact
approved target, backup, source review, scanner disposition, binary manifest,
or owner build/copy approval, so the first-DLL gate remains closed.

## Open decisions and non-decisions

This contract intentionally does not decide:

1. Whether Random fails closed to Standard unless the game was started through the
   Bit Wrecked launcher.
2. The customer-facing wording for `ACTIVE + Vanilla`.
3. The transport used for a future launcher-to-runtime policy handoff.
4. Whether the selected game-owned CVar marker survives every required runtime
   save, crash, reload, reconnect, death, and server/client boundary.
5. Whether EAC, clean-client, listen-server, or dedicated-server operation is
   supportable.

No implementation may treat a proposed value in an older document as an
answer to one of these decisions.

## Phase 0A acceptance gate

Phase 0A is ready for review when this document, the UX-0/UX-1 model, the
negative-test matrix, the software-assurance contract, and the evidence links
agree on the same boundaries. It is not complete merely because the files
exist. Runtime compilation, live copying, and gameplay claims remain blocked
until the owner/review gate is explicitly recorded.
