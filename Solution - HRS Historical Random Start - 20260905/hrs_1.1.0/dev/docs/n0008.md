## Solution Capsule Ownership Contract

Historical Random Start is managed as a self-contained **solution capsule**.
The capsule model is analogous to a container ownership boundary, not a claim
that the game itself runs in a container:

- the host is the licensed 7 Days to Die installation and user-controlled
  Steam environment;
- the capsule is only the Historical Random Start-owned launcher/tooling,
  policy/result records, runtime payload, manifests, and recovery metadata;
- the capsule declares every installed artifact and approved destination;
- the base game, Steam, saves, worlds, shared Harmony/runtime layers, and other
  Bit Wrecked solutions remain external to the capsule; and
- external dependencies may be detected and compatibility-checked read-only,
  but this capsule never installs, modifies, repairs, disables, or removes them.

The capsule installation manifest is the sole ownership authority for install,
state measurement, repair, and Remove from Game. A file is not owned merely because
it is nearby, has a similar name, or appears necessary. Unknown or changed
artifacts are reported and left untouched.

### Capsule state metric

The upper status area presents one plain-language capsule state, with technical
details behind one disclosure control. The core state model must distinguish at
least:

- `Not installed`;
- `Installed — configuration incomplete`;
- `Ready — Standard`;
- `Ready — Random`;
- `Runtime lane unconfirmed`; and
- `Completed — no further relocation`.

The primary sentence carries meaning without color. Hashes, owned-file lists,
dependency observations, policy revision, and evidence detail stay under the
single Details disclosure. `Launch Game` remains available independently; an
incomplete configuration launches the game but leaves the mod inactive and
shows `Configuration incomplete — mod not enabled`.

### Remove from Game

`Remove from Game` is an independent secondary action under Details and is
available whenever the game is closed. It requires clear confirmation. It may
remove only deployed game artifacts that:

1. are named in this solution's installation manifest;
2. are inside the solution's approved owned destinations; and
3. still satisfy the expected identity or an explicitly reviewed owned-drift
   rule.

Remove from Game must not remove or modify shared Bit Wrecked tooling, other
solutions, the base game, Steam, Harmony/shared runtime layers, saves, worlds,
XML, or unrelated mods. It must not use broad name matching, parent-folder
deletion, or inference from adjacency.

After removal, the tool verifies every solution-owned artifact deployed into
the game is absent and reports `Historical Random Start removed from game`.
The portable BAT/manager, local notes, history, and audit evidence remain. The
manager is not installed into Windows, and no system files are removal targets.
Deleting the portable manager is a separate manual user action. The result does
not claim that the game is vanilla or unrelated gameplay state was reversed.
If an owned artifact cannot be verified or safely removed, report a bounded
incomplete removal with the exact remaining item; never broaden deletion.

### Mod coexistence and collision contract

The successful Phase 1A run provides narrow evidence that the guarded probe
used native game/ModAPI behavior, did not patch or modify Harmony, and left the
measured game-managed and foreign-mod aggregates unchanged in that pinned run.
It does not prove universal compatibility with every current or future mod.

Historical Random Start must not merge into, write through, repair, replace,
disable, reorder, or remove `0_TFP_Harmony`, a shared runtime layer, or any
unrelated mod. Its capsule receives one uniquely named owned mod directory and
one uniquely named assembly identity. Shared dependencies remain read-only
compatibility observations.

Before install or update, the capsule preflight checks only the bounded
collision surface needed for safe ownership:

- the intended capsule Mod folder does not contain unknown or unmanifested
  files;
- an existing capsule folder and its manifest, if present, match a recognized
  owned version or explicitly supported upgrade path;
- the capsule's ModInfo identity, assembly name, and declared policy/result
  identities do not collide with another installed artifact;
- the pinned game/API and declared shared-runtime compatibility signals match;
- no known installed mod declares the same capsule identity; and
- any known first-spawn/relocation collision discovered through bounded static
  metadata is surfaced for review.

The preflight must not recursively classify, hash, copy, quarantine, or alter
all unrelated mods merely to claim compatibility. Unknown neighboring mods are
not automatically incompatible; they remain an honest unproven compatibility
surface. Runtime guards and the evidence campaign must still detect duplicate
lifecycle behavior, another first-spawn mover, or unexpected final-position
changes.

If the intended capsule folder contains unknown files, recognized owned files
have unapproved drift, or an identity collision exists, install/update stops
before overwrite and reports `Existing installation requires review` with a
bounded reason. It never widens authority to Harmony or another mod. The user
may still launch the game; Historical Random Start remains inactive until its
capsule state is reviewed and valid.

## Goal

Create a legitimate survival-start mechanic that changes how the initial start
location of a genuinely new character is chosen. Standard preserves the
ordinary game start, while Random broadens selection among authored
startpoints. Later Random extensions may select a validated ground or Wasteland
rooftop location without creating another policy type.

The mechanic must work through normal game/runtime behavior. It must not enable
Developer Mode, issue console teleport commands, set cheat flags, alter reward
logic, or require direct edits to the live `Data/Config` payload.

## Player-Facing Contract

For a fresh character using either start choice:

1. The game creates the character and begins the ordinary world-spawn flow.
2. The helper detects the first valid player spawn.
3. Standard leaves the ordinary game start untouched.
4. Random selects from the native authored spawnpoint list with broader
   selection.
5. A later expanded-Random feature may select a bounded validated ground
   location or, only after its own gate, an allowlisted Wasteland roof.
6. The core path requests exactly one native candidate. Any ambiguity or
   verification failure consumes the attempt and never rerolls.
7. Placement is deferred until after the spawn callback. The runtime brackets
   one native position call and existing-observer synchronization with
   same-callback semantic snapshots, then performs bounded read-only spatial
   verification. An above-ground drop is experimental and never the default.
8. After its separate Phase 1B gate, Random's opening stone-shovel trader quest
   points to the nearest
   valid trader from the player's new area rather than forcing a return toward
   the normal pine-forest start route.
9. After its separate Phase 1C gate, the player may leave biome relief off,
   suppress only the hazard
   family resolved from the initial landing biome, or suppress the reviewed
   Burnt Forest, Desert, Snow, and Wasteland families. Both safeguard choices
   begin unchecked and cannot be selected together.
10. Temporary arrival protection may cover a proven placement hazard.
11. Protection ends after the player is grounded and receives a short grace
   period, with an absolute maximum of 15 seconds after placement.
12. Persistent one-time markers prevent relocation or starter-trader routing
    from repeating on reload, reconnect, or ordinary respawn.

Existing characters, ordinary reloads, and normal deaths are out of scope for
relocation. They are explicit no-action paths, not merely untested user flows.

## Proof-First Product Strategy

The project follows a proof-first, two-lane strategy. Launcher polish must not
outrun evidence that the current game can identify and relocate one new
character safely and exactly once.

### Core completion boundary — finish this before adding features

The first complete product increment is one narrow vertical slice from what
the player sees to the already proven atomic relocation mechanism:

```text
player manually enters exact new-game name
  -> player chooses Standard or Random
  -> launcher validates and saves one bounded policy
  -> runtime validates the same schema and exact game name
  -> genuinely-new-player first eligible arrival only
  -> Standard performs no selection or placement
  -> Random invokes the proven one-candidate atomic relocation state machine
  -> persistent per-player/game completion prevents every later repeat
  -> launcher exposes a sanitized categorical outcome
```

For this increment, "complete" means the entire chain works and is evidenced
in the pinned local single-player lane. It does not mean that every planned
Historical Random Start feature exists.

The core increment contains only:

- one manually entered `ExactNewGameName`; no automatic save discovery is
  required to activate it;
- exactly two choices, `Standard` and `Random`;
- a versioned, bounded, fail-closed launcher/runtime policy contract;
- one genuinely-new-player first-arrival eligibility decision;
- the existing native-authored-spawnpoint, one-candidate, no-reroll atomic
  relocation mechanism for Random;
- durable Absent/Reserved/Completed/Invalid marker behavior scoped to the
  player and game;
- no second selection or placement on reload, reconnect, death, respawn,
  duplicate callback, launcher restart, or ordinary continued play;
- a sanitized categorical result with no raw private identity or machine path;
- rollback and recovery evidence; and
- an end-to-end test record linking the launcher choice, saved policy, runtime
  decision, placement result, persisted marker, and no-repeat reload.

Everything else is post-core. Trader routing, biome safeguards, automatic
world discovery, `DiscoveredGame`, `AllGames`, multiplayer/server enablement,
arbitrary-coordinate search, distance agency, drops, arrival protection, and
rooftops must not be connected merely because their controls or designs
already exist.

### Layered post-core roadmap

After the core completion gate passes, add capabilities in this order unless
new evidence requires a recorded reordering:

1. **Core hardening and clean replication** — repeat the exact vertical slice
   from a clean isolated baseline and close recovery/error-path gaps.
2. **Phase 1B: nearest opening trader** — retarget only the opening Journey to
   Settlement destination after a completed Random start.
3. **Phase 1C: optional biome safeguards** — connect the two existing
   default-off preview choices only after per-character authority, persistence,
   cleanup, and isolation are proven.
4. **Discovery and broader local targeting** — add read-only game discovery,
   then separately enable `DiscoveredGame`; keep existing players ineligible.
5. **Multiplayer/server and `AllGames`** — prove authority, concurrency,
   reconnect, isolation, and client requirements before enabling either.
6. **Expanded Random placement** — add bounded coordinate search and distance
   agency without changing the two player-facing start choices.
7. **Arrival extensions** — add drop/protection only if the selected candidate
   class requires them and cleanup is independently proven.
8. **Wasteland rooftops** — keep as the final optional candidate sub-lane with
   live structural validation and its own rollback evidence.
9. **Packaging and public release** — only after the chosen capability set has
   a clean install, license, security, compatibility, and claims review.

A later layer may consume the stable core contract but may not weaken or
silently rewrite it. Failure of a later layer leaves the last proven lower
layer usable and does not invalidate the core.

### Experimental sub-lane — Wasteland Rooftop Start

Rooftop placement is an optional experimental Random extension. It does not
create another player-facing policy choice. It is considered only when Random
and its separately approved rooftop capability are both explicitly enabled.

The rooftop dataset is a candidate index, not the final placement authority.
Each versioned record may contain:

- prefab or asset identity;
- a local candidate point on the roof;
- expected roof height and surface type;
- player-footprint and headroom requirements;
- Wasteland eligibility and a bounded selection weight; and
- dataset version and evidence status.

The runtime must still locate the actual generated POI or asset instance,
apply its position and rotation, and validate the live block geometry. Asset
height data alone cannot prove that a roof exists, is intact, is reachable by
the collision system, or is safe in the current world.

Rooftop selection uses bounded Monte Carlo sampling: choose randomly among
dataset candidates and actual world instances, then accept only candidates
that pass live validation. “Random” means random among valid rooftop
candidates, not random coordinates and not an unbounded retry loop.

A rooftop candidate is accepted only when all of the following are true:

- the actual location is in the Wasteland biome;
- the roof belongs to the allowlisted asset or prefab instance;
- the target block has solid support and a valid walkable surface;
- the player has sufficient headroom and collision clearance;
- the position is not liquid, void, cave, unstable, embedded, or over an unsafe
  edge;
- the position does not conflict with a claim, player, protected area, or
  other safety rule; and
- the server can confirm the final position before completing the transaction.

Ordinary POI candidates remain rejected. A rooftop is allowed only through the
explicit allowlist and rooftop validator. If the live world cannot confirm the
asset, roof, height, support, or final placement, the candidate is rejected and
the bounded fallback path is used.

Direct placement onto the validated roof surface is preferred. A dramatic drop
from above is not part of the core rooftop proof. If a later drop test proves
useful, arrival protection must begin before placement, cover the full arrival
sequence, and be removed only after stable grounding plus the grace period.
Protection is a safety envelope, not a substitute for roof accuracy.

The product is an external Windows launcher/module host stored with the
player's local Downloads copy. It is not a Git-based player distribution tool

Reuse the proven Wasteland launcher/framework shell. Replace the gameplay

### World policy index

- Keep a small external policy index with versioned, unambiguous target
  identity and policy revision. A raw path or display name alone is not a
  durable identity for an existing save.
- Do not modify world files merely to store launcher policy.
- Show the five most recently modified world saves by default.
- Provide separate actions to browse for another world or load the full list.
- Show `World`, `Status`, and `Spawn Policy` clearly.
- Newly discovered worlds default to red/bypassed with `Vanilla` selected.

### Target scope and fixed first-arrival trigger

Target scope, start policy, and lifecycle eligibility are independent:

- target scope answers **where** policy applies;
- Standard or Random answers **what** policy applies; and
- the fixed new-player gate answers **when and to whom** runtime work is
  permitted.

Planned target scopes are:

1. `ExactNewGameName` — one not-yet-created game armed by an exact name typed
   in the launcher;
2. `DiscoveredGame` — one existing game/save selected from the read-only index;
   and
3. `AllGames` — every otherwise eligible game in a configured local/server
   scope.

Every scope retains the same invariant: act only for a genuinely new player's
first eligible arrival, at most once for that player/game. Established players
are never moved on load, reconnect, death, respawn, or continued play.
`AllGames` broadens only target coverage; it does not broaden the trigger.

The first bridge enables only `ExactNewGameName` in the proven local
single-player lane. The launcher supplies a required exact-name field and Copy
Name action; the player uses that value on the game's New Game screen. Blank,
whitespace-ambiguous, colliding, or mismatched names fail closed. After
creation, a rescan may replace the provisional named presentation with the
authoritative discovered identity and categorical outcome.

`DiscoveredGame` mutation, `AllGames`, and multiplayer/server use remain
disabled until their separate state, authority, concurrency, reconnect,
per-player isolation, and clean-client gates pass. The single behavioral
authority is the `Canonical Policy Eligibility Grid` (`PEG-01` through
`PEG-14`) in `n0009.md`. Other documents and
implementations reference those row IDs rather than maintaining competing
grids.

### Active/bypassed state

- Green means `ACTIVE — custom spawn policy`.
- Red means `BYPASSED — Standard start`.
- Text must communicate the state; color is reinforcement, not the only signal.
- Red/bypassed worlds receive no custom gameplay action. The helper may load,
  validate, record a categorical bypass, and return.
- `Standard` (internal `Vanilla`) is an explicit policy that performs no
  custom gameplay behavior.

### Save and launch workflow

1. The owner selects an existing discovered target or prepares one exact New
   Game name, then selects Standard or Random while the game is closed.
2. The launcher presents a clear plain-language summary and confirmation.
3. After its separate bridge approval, Save writes one small local versioned
   policy and a saved-settings record through staged validation, atomic
   replacement, immediate readback, and bounded rollback. It does not create a
   Git commit or publish anything.
4. The result opens in a detail popup with the saved world, previous and new
   policy, timestamp, launcher version, and result.
5. The launcher exposes one always-visible `Launch Game` button that requires
   Steam running and can be activated only by the local person who opened the
   manager. No AI, timer, other control, or automatic flow may activate it.
   Readiness and normal non-EAC instructions remain in the upper status area.
6. The runtime helper independently validates the saved schema, build, target,
   revision, scope, policy, lifecycle, authority, and per-player marker before
   caching immutable session intent.

The launcher is the control plane; it never moves a player or calls the live
mechanic. The DLL is the runtime/data plane; it never owns dialogs or infers
player intent. A separately reviewed, sanitized categorical result projection
may later report BYPASSED, RESERVED, COMPLETED, FAILED, or INCOMPATIBLE back to
the launcher. The launcher must not parse or rewrite save internals merely to
read the authoritative in-save marker, and the physical result channel is not
yet approved.

Steam account operation and automated game launch are outside both planes. The
AI must not activate Launch Game, and the launcher must not automate, attach to,
sign in to, or send commands beyond the direct user's reviewed launch handoff.
A saved policy is inert until the owner clicks Launch Game. This is a
user-computer and account boundary, not merely a convenience feature.

EAC is also exclusively user-controlled. The package may detect and report the
approved runtime lane, but it must never disable, lower, reconfigure, bypass,
patch, stop, or otherwise change EAC. Before launch, the frontend states that
the normal non-EAC Steam option is required; it does not claim to have verified
the state. After launch, Random remains ineligible unless an independently
reviewed runtime signal positively confirms the approved non-EAC lane.

If EAC is active, the lane cannot be determined, or the helper never loads,
the system performs no reservation, selection, or placement. When a result can
be projected safely, it reports `NON-EAC REQUIRED` or
`RUNTIME LANE UNCONFIRMED` and tells the user to exit normally and independently
relaunch through Steam's normal non-EAC option. Absence of a runtime result is
not proof of EAC state and must not become a compatibility claim.

There are no pending settings. If the game is running, the launcher keeps the
last saved policy, allows read-only viewing, and disables its own save,
activation, modification, and launch-policy controls. It does not lock the
game or game files.

### Simple policy choices

The first launcher presents exactly two clear choices:

- `Random`: use the existing spawnpoint list with broader selection.

Wasteland rooftops and broader safe-world search are future Random candidate

### Opening trader continuity

Nearest-trader continuity is part of Random, not another player setting.
Standard leaves the opening quest completely untouched.

The current V3.1 starter quest is `quest_whiteRiverCitizen1`, Journey to
Settlement. Its phase-one `trader` destination is currently filtered to
`pine_forest`, and normal completion awards `500` XP and one stone shovel. For
a character who completed an authorized Random first placement, route only
that destination to the closest valid current-world trader across any biome.

Use the player's authoritative position when the exact quest is accepted. If
the quest already exists when Random placement completes, use the confirmed
final placement position. Use the native trader registry, native authored POI
selector, and actual prefab bounds; do not invent coordinates. Exact-distance
ties use a stable current-world key rather than another random roll.

The future runtime should subscribe to the player's native `QuestAccepted`
event and match only the exact quest, phase, and `trader` objective. The
current-build event occurs before `QuestJournal.AddQuest` persists its position
data, and `ObjectiveGoto.SetLocation(...)` exposes a narrow native destination
path. Those signatures are static feasibility evidence only; server authority,
client synchronization, save durability, and turn-in still require a staged
Phase 1B proof.

Do not delete, abandon, clone, restart, complete, or re-add the quest. Do not
change its shovel, XP, challenge completion, skill points, quest tier, later
trader-to-trader flow, trader inventory, or player position. Respect the native
`TraderToTraderQuestsEnabled` setting; if the game does not add the quest, the
mod does nothing.

Reserve one per-character routing attempt before selecting a destination. A
duplicate event, failure, uncertainty, reload, reconnect, or death never
rerolls. If no legal trader or authoritative synchronization can be proven,
leave the native quest untouched and record a sanitized fallback reason.

Dangerous-biome behavior is an explicit Random safeguard decision. Two
mutually exclusive safeguard checkboxes begin unchecked, remain visible and
editable under both start choices, and have runtime authority only under
Random.
Previously saved valid world settings are respected on later launches.

### Random-start safeguards

Random is supposed to create a difficult and surprising opening, not an
unavoidable environmental countdown before the player has a chance to react.
Expose one simple, aligned row under `Random-start safeguards (optional)`:

- `Starting biome only` — unchecked by default; and
- `All dangerous biomes` — unchecked by default.

Do not grey out or hide this row under either start type. Players may prepare
their Random preference while Standard is selected. The controls are mutually
exclusive: selecting one clears the other, while clearing both restores the
default of complete vanilla biome hazards. The UI must plainly state that
neither selection can alter Standard.

`Starting biome only` resolves once from the authoritative initial Random
landing. If that landing maps to Burnt Forest, Desert, Snow, or Wasteland, only
that one biome-owned hazard/storm family is recorded for suppression for that
character. The other three dangerous-biome families remain fully active,
including when the character later enters them. Returning to the original
dangerous starting biome still uses the resolved relief. If the initial biome
has no reviewed dangerous hazard family, no custom relief is created.

`All dangerous biomes` resolves all four reviewed families for that eligible
Random-start character. The intended V3.1 target families are
`buffSnow_Hazard*`/`buffSnow_Storm*`,
`buffBurnt_Hazard*`/`buffBurnt_Storm*`,
`buffDesert_Hazard*`/`buffDesert_Storm*`, and
`buffWasteland_Hazard*`/`buffWasteland_Storm*`.

The safeguards do not turn off a biome itself. Weather visuals, ordinary
temperature, lootstage, gamestage, zombies, POI occupants, falls, collision,
hunger, thirst, infection, and ordinary damage remain part of the game. This
keeps a Wasteland rooftop start survivable through skill and luck without
turning it into god mode.

The suppression scope is per eligible character, not global XML, not a whole
server, and not every player in the save. Standard ignores these fields and
remains unchanged. Existing characters do not gain protection merely because
the world policy contains a safeguard scope.

The policy value is the strict enum `None`, `ArrivalBiome`, or
`AllDangerousBiomes`. `None` creates no custom mask. `ArrivalBiome` resolves to
either no mask or exactly one of the four reviewed family bits after the
candidate's biome is authoritatively known. `AllDangerousBiomes` resolves to
all four bits. Arbitrary family combinations are invalid and are never exposed
as player choices.

For `ArrivalBiome`, any required suppressor for the candidate's dangerous
starting biome must be proven before placement. For `AllDangerousBiomes`, all
four current-build suppressors must be proven before placement. If required
suppression cannot be proven or restored cleanly, fall back before placement;
do not land the player and hope a broad debuff remover works.

No live `Data/Config` or biome XML edit is permitted. The future runtime must
use a narrow server-authoritative, game-API route and a versioned per-character
eligibility/mask record. Disabling the policy or removing the runtime leaves no
active custom immunity; ordinary game biome behavior resumes.

V3.1 also exposes one native whole-world `BiomeProgression` setting. The mod
must read and respect that setting but must never silently change it to satisfy
a safeguard scope. If the native setting is off, no custom suppressor is
needed. If it is on, either selected scope still requires the narrow
per-character proof above; a global toggle is not a substitute.

This is an Alpha 6-style comfort choice, not a claim that original Alpha 6 code
or exact historical internals were copied.

### Exact vanilla boundary

Standard (internal `Vanilla`) is an exact gameplay no-op. It does not call the
candidate selector, placement path, observer synchronization, trader routing,
safeguard, protection, slider, or custom-coordinate paths and does not mutate
the per-player relocation marker. The helper may still load, validate the
policy/environment, expose a categorical BYPASSED result, and return. Random
runtime authority exists only when the exact target scope and every fixed gate
also match.

## Player Agency

The player should eventually be able to choose how far a Random opening pushes
them from the ordinary start. Add a future `Random Distance` control with this
intended shape:

| Setting | Meaning |
| --- | --- |
| `0%` | Close to the ordinary starting area. |
| `25%` | Nearby outskirts with light separation. |
| `50%` | Moderate random distance. |
| `75%` | Remote random start. |
| `100%` | Maximum valid distance from ordinary spawn. |

The slider changes distance and intensity only. It must not disable the safety
validator. Water, caves, void, invalid terrain, unsafe placement, and other
hard failures remain rejected at every setting.

For rooftop candidates, the distance setting may constrain which Wasteland
instances are eligible, but it does not guarantee a roof will be found or
override the rooftop validator.

Possible later controls:

- solo versus party-together placement;
- minimum distance from other players;
- biome danger preference; and
- server-locked versus player-selected agency mode.

The first implementation should prefer a server configuration control because
it is simpler, easier to test, and does not require every clean client to carry
a custom UI. A per-player in-game slider is a later feature that may require a
runtime UI or client-side component.

The launcher owns the policy choice. The runtime helper does not need an
in-game settings screen. The active session policy may change between launches,
but not while a game is running.

## Random Location Rules

Random uses the native authored spawnpoint list and does not edit it.
The broader candidate rules below apply only to the experimental expanded-
Random lane, not to Standard or the initial authored-spawnpoint proof.

The expanded-Random location finder must:

- choose random X/Z coordinates rather than a fixed spawn list;
- respect the generated world's usable bounds;
- find a solid surface with enough headroom;
- reject water, deep liquid, caves, void, bedrock-level placements, steep or
  unstable terrain, and invalid height results;
- reject POI or protected-area placements when the current API can identify
  them;
- avoid active player claims or bases when that check is available;
- ensure the target chunk/terrain is ready before final placement; and
- stop after a bounded number of attempts and fall back to vanilla spawn.

The first prototype should expose a conservative allowed-biome and distance
policy. “Truly random” means random among valid candidates, not random among
unsafe coordinates.

For the rooftop sub-lane, the same rule applies: sample from the versioned
dataset and discovered world instances, then validate the actual roof before
placement. A missing, changed, damaged, occupied, or otherwise unsafe roof is
not a valid candidate.

## Arrival Protection

Protection is a safety envelope, not a permanent god-mode feature.

Protection and above-ground drop behavior are not required for the core
authored-spawnpoint proof. Prefer direct validated grounded placement first.
Add protection only when a later test demonstrates a specific arrival hazard
or when the experimental drop lane is explicitly enabled.

Arrival protection is separate from Random-start safeguards. The former is a
short placement envelope capped at 15 seconds; the latter is a saved,
per-character scope covering either the resolved initial dangerous-biome
family or all four reviewed families. Neither may become broad damage
immunity.

- Apply it before or at the moment of placement.
- Cover fall, collision, terrain, environmental, and hostile damage relevant
  to the arrival sequence.
- For a rooftop arrival, do not remove it while the player is falling, clipped,
  sliding, or otherwise not stably grounded on the roof.
- Do not use Developer Mode or a debug invulnerability command.
- Do not allow protection to stack or survive as an unintended permanent buff.
- Begin the grounded/grace transition only after the player is actually placed.
- Never remove protection while the player is still falling or embedded in terrain.
- Enforce a hard maximum of 15 seconds so a bug cannot create unlimited safety.
- Clear pending state correctly on disconnect, failed placement, and reload.

If the current runtime cannot reliably detect grounded state, use a conservative
fixed timer only as a fallback and document that limitation in the test result.

## Progression and Reward Safety

The helper must not:

- enable Developer Mode or debug state;
- use player-facing teleport commands;
- alter XP, loot, quest rewards, starter items, skill points, or gamestage;
- mark quests complete or bypass the normal tutorial unintentionally; or
- relocate an established character or perform more than one selection or
  placement attempt for the same new-player eligibility event.

- Prevent repeated event handling, state replay, and unbounded rerolls.

### State-machine discipline

The persistent marker is interpreted only as Absent, Reserved, Completed, or
Invalid. Volatile runtime state may additionally distinguish Eligible,
PendingPlacement, Verifying, Failed, and Bypassed. Transitions must be
idempotent and traceable to a `PEG-*` eligibility row.

- A player may have at most one active relocation transaction.
- Reservation must be persisted before candidate selection; Completion is
  written only after semantic and spatial verification pass.
- Disconnect, reload, exception, or timeout must leave the player in a known
  safe state.
- If a later lane earns arrival protection, it must have both grounded-state
  removal and a hard expiry.

### Defense in depth

For the core lane, bind one game-owned candidate to the pending attempt, use
the native placement path, require same-callback semantic equality, and then
verify containing-chunk readiness, native safety, and final position through a
bounded settling window. Expanded coordinate/rooftop lanes additionally
require independent sampling-time and pre-placement geometry validation. Do
not rely on one client report or arbitrary timer.

### Auditability and integrity

- Log only sanitized event outcomes, configuration bands, rejection categories,
  state transitions, and elapsed time.
- Do not log raw private identity data or full world/player snapshots.
- Make package contents explicit and reproducible.
- Record hashes for release archives and keep recovery artifacts separate.
- Preserve evidence for failed tests as well as successful tests.

### Proven logging model

Reuse the Wasteland launcher logging model:

- `Layered Reasoning Log / Recent Actions` is runtime-only by default;
- no log file is created silently;
- validation, confirmation, policy, lock, save, and launch entries are tagged;
- `Persistent log` is independent from the visible runtime log;
- `Choose Log File` requires explicit consent before writing;
- turning persistence off never deletes an existing saved log; and
- logs remain local and contain no secrets or private identity data.

The saved-settings record is separate from the optional persistent activity
log. It is an internal support record for explaining what was saved, not a Git
commit, upload artifact, or player-to-player distribution mechanism.

### Threat cases to test

Treat these as failures, not edge-case curiosities:

- duplicate spawn events causing a second selection or placement;
- disconnect/reconnect causing a reroll or permanent protection;
- a player forcing a configuration value outside allowed bounds;
- a search loop causing excessive chunk generation or server load;
- placement inside terrain, liquid, a POI, a claim, or a hazard;
- client/server disagreement about the final position;
- an exception leaving a player invulnerable; and
- an archive or installer containing files outside the approved package scope.

Scouting uses a disposable save. Flight, god mode, developer mode, and
invulnerability are permitted only to reach and inspect candidates. The player
should disable flight and stand normally at the proposed street-level landing
position before the player-view screenshot when practical. Every scouting
record must be labeled:

> DEV scouting only — flight/invulnerability enabled; not live spawn or
> survival proof.

Each record requires a stable point ID, zone/biome, world/map identity,
observed X/Y/Z, street-level screenshot, map screenshot, surface type,

### 2026-09-01 human-in-the-loop carousel value

The carousel deliberately combines automation with continuous human
observation. Full unattended automation is not the objective because game
telemetry cannot represent every condition that makes a starting location
unacceptable to a player.

Automation provides the repeatable measurement layer:

- stable IDs and deterministic order;
- chunk priming and the timed second teleport;
- requested and actual coordinates;
- health, movement, bounds, and grounded-state checks;
- fixed dwell time, first-failure stop, and exact-origin restoration; and
- raw forensic events, results, hashes, rejection state, and resume position.

The operator provides the experiential evidence layer. Human observation has
already identified hazards that coordinates or simple stability measurements
could misclassify: pole-top arrivals, floating beneath formed prefab blocks,
swollen or cratered terrain, hostile overlap, partial burial, rooftops, and
landings that are numerically close but visibly janky or unusable.

A candidate therefore needs both kinds of evidence. An automated safety
failure is not overridden merely because the second teleport looked better;
the game must report a real stable grounded state. Likewise, a telemetry pass
does not override a clearly unsafe human observation. Setup contamination such
as fly/no-collision, movement, health loss, or a bad saved origin is preserved
as invalid setup evidence and never used to reject a destination.

Keeping the owner in the loop costs attention and model context, but that cost
is justified during discovery because it produces a safer approved pool and
teaches the project which observations can later be automated reliably. The
efficient operating balance is to automate repetitive movement and objective
guards, ask the human only for player-facing judgment at stops, preserve raw
evidence, and append a compact row to the carousel handoff catalog rather than
writing a narrative manifest for every routine run.

This method works because neither participant is asked to provide evidence it
cannot observe well: the runtime measures game state, the player judges the
visible experience, and the durable record keeps the two signals distinct.
