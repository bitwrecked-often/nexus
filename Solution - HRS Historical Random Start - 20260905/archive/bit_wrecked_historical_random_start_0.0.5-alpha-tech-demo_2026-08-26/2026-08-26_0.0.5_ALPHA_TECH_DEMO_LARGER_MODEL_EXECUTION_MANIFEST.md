## 1. Mission

Prepare the active Historical Random Start lane for an honest `0.0.5-alpha`
technical demonstration while improving situational awareness for every future
human or AI worker.

The larger model must make the active lane internally self-consistent,
preserve the established execution pipeline, and produce evidence that clearly
distinguishes source, generated output, historical evidence, private material,
and release candidates.

This assignment does not authorize publication, Nexus upload, live game
mutation, game launch, save/world access, or modification of the frozen
`0.0.1-alpha` lane.

## 2. Environment Truth

This is a versioned working-directory convention inside a live 7 Days to Die
installation. It may display Git decorations and repository-like organization,
but folder names—not branches—currently communicate version authority.

The larger model must not assume that Git status alone defines the safety
boundary or that every file under the game installation is project-owned.

### Lane authority

| Lane | Authority | Mutation rule |
| --- | --- | --- |
| `0.0.1-alpha_nexus-review_2026-08-26` | Frozen Nexus-review reference | Read and hash only; never edit, rebuild, reformat, clean, or regenerate. |
| `0.0.5-alpha-tech-demo_2026-08-26` | Sole active development lane | Routine source, documentation, tests, and contained build work are allowed. |

At the start of execution, verify that both version folders exist and that the
frozen lane still matches the Nexus reference. Record hashes or a deterministic
tree comparison without changing either reference.

## 3. Non-Negotiable Architecture Rule

Do not add another main function, application entry point, launcher, parallel
orchestrator, alternate state authority, or competing deployment path.

New `0.0.5` behavior must enter the existing pipeline as bounded features or
modules with explicit inputs, outputs, failure behavior, ownership, and tests.

Before proposing a new component, identify:

1. the existing pipeline stage that owns it;
2. the existing main entry point through which it is reached;
3. its state and filesystem boundary;
4. its fail-closed behavior;
5. its test seam; and
6. how it can be removed without affecting unrelated features.

If no existing stage can own a proposed feature, stop and document the
architectural conflict. Do not solve the conflict by creating a second main.

## 6. Work Package B — Honest 0.0.5 Version Conversion

The active folder began as a byte-identical copy of `0.0.1-alpha`. Convert only
the active lane to an internally consistent `0.0.5-alpha-tech-demo` identity.

First inventory every version-bearing location and classify it:

| Classification | Treatment |
| --- | --- |
| Current product/runtime/manager/package identity | Update to the approved `0.0.5-alpha-tech-demo` form appropriate to that field's grammar. |
| Historical release fact or filename | Preserve; do not rewrite history. |
| Schema, contract, or document version | Change only if the contract itself changes. |
| Test fixture value | Update only when it represents current product identity; retain boundary/grammar examples. |
| Frozen preview identity `0.0.7-preview` | Preserve as historical preview truth unless that preview is intentionally replaced. |
| Dependency/reference version such as Wasteland `4.1.1` | Preserve. |

Do not perform blind global replacement. Produce a version inventory showing
the old value, proposed value, semantic role, and decision for every changed
location.

The runtime `ModInfo.xml` may require a numeric game-compatible version while
manager/source/package metadata may permit a prerelease label. Document the
chosen mapping instead of forcing one string into incompatible formats.
