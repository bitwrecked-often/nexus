## QA-004 deployment-integrity contract

### Valid installed deployment

A valid installed deployment is an exact, manifest-approved owned capsule at:

```text
<validated game root>/Mods/mod/
```

Its complete allowed shape is:

```text
d0163.dll       required static file; exact approved size/hash
ModInfo.xml                     required static file; exact approved size/hash
Bridge/                         only allowed child directory
Bridge/policy.v1.json           optional mutable owned state; valid schema/content
Bridge/result.v1.json           optional mutable owned state; valid schema/content
```

`d0163.dll` and `ModInfo.xml` must each match exactly one entry
in the deployment manifest constructed from the approved candidate payload.
For the frozen QA baseline, the runtime hash is the frozen hash above; a later
DEV build may be approved only through its new deterministic build/package
record. Mere file, release-root, or `Bridge` existence is never proof of
readiness.

No other file or directory is allowed anywhere inside the owned release root.
Reparse points are invalid. Missing static files are incomplete. Unknown files
or directories are conflicts. Size/hash mismatch is drift. Invalid policy or
result content is drift. An absent release root is `NotInstalled`, not an error
and not ready to Apply.

### Authoritative status states

The manager must derive UI state and capability from one fresh deployment
inventory result, with at least these operator-visible distinctions:

| Inventory result | Operator state | Apply |
| --- | --- | --- |
| `InstalledValid` | Installed payload verified | Enabled only if every other Apply gate passes |
| `NotInstalled` with an approved complete source payload | Verified payload available; installation required | May enter the existing controlled install flow, then must verify before policy work |
| `NotInstalled` without an approved complete source payload | Not installed / approved payload unavailable | Blocked |
| `Incomplete` | Installed payload incomplete | Blocked |
| `Drift` | Installed payload stale, altered, or invalid | Blocked |
| `Conflict` | Extra/unknown owned content or reparse point | Blocked |
| `ManifestInvalid`, `PathInvalid`, or `InventoryFailed` | Deployment cannot be verified | Blocked |

Error/status copy must be specific enough to distinguish not installed,
missing, stale/hash mismatched, unknown/extra, and validation failure. It must
not claim setup ready from `Bridge` existence.

### Refresh and Apply gates

1. `Update-HrsStatus` (or its bounded replacement within the existing manager)
   obtains or validates the approved deployment manifest and calls
   `Test-HrsDeploymentInventory` for the validated game root.
2. Apply capability is computed from `InstalledValid` plus the existing game-
   closed, game-root, exact-name, ownership, and other safety gates.
3. If `NotInstalled`, the existing controlled install path may copy only from
   an approved, complete, hash-validated payload. It must verify the installed
   inventory as `InstalledValid` before continuing.
4. After operator confirmation and immediately before `Write-HrsPolicyFile`,
   Apply repeats `Test-HrsDeploymentInventory` using the same approved manifest
   and game root.
5. Any second-check result other than `Valid=true` and
   `State=InstalledValid` aborts without writing or replacing policy or result
   state. This is the required bounded TOCTOU defense.
6. The pre-write check is mandatory even if status refresh, initial Apply
   validation, or installation verification just succeeded.

The approved manifest and candidate identity used by status, install, and
pre-write validation must be the same validated object for that manager
session/action. A stale or missing manifest fails closed.
