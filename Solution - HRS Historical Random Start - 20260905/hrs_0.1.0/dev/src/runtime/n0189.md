# Phase 1 Observation Probe Design 0.0.1

Product: `Historical Random Start - Alpha 6 Method`  
Private DEV identity: `BitWrecked_HistoricalRandomStart_DEV`  
Status: Design only; no runtime source or binary exists

## Purpose

Phase 1 answers one narrow question: can the installed game reliably expose a
new-character spawn event on the authoritative server path without the probe
changing gameplay or save state?

The probe is observation-only. It cannot implement Random placement. A clean
Phase 1 result is required before Phase 1A may attempt one native authored-point
relocation.

## Non-negotiable behavior boundary

The Phase 1 probe may only:

- initialize through `IModApi`;
- receive `ModEvents.PlayerSpawnedInWorld`;
- compare the loaded build and current target with an exact private allowlist;
- classify authority, `RespawnType`, entity resolution, and duplicate events;
- maintain bounded in-memory counters for the current process; and
- emit bounded, sanitized messages through the normal game `Log` API.

It may not select a spawnpoint, set a CVar, relocate an entity, add a buff,
change a quest/reward/XP/progression value, write a file, inspect player
identity, invoke a command, patch a method, access the network, or launch a
process.

## Compatibility guard

The probe is compiled for exactly:

- game display version `V 3.1.0 (b14)`;
- Steam build ID `24436778`; and
- `Assembly-CSharp` MVID
  `acb580d9-e1ab-497d-a8dc-47e47c1fc300`.

At runtime it compares `typeof(IModApi).Assembly.ManifestModule.ModuleVersionId`
with the pinned MVID before registering active observation behavior. A mismatch
produces at most one sanitized incompatibility line and leaves the module inert.
The SHA-256 remains a build/test evidence requirement; the runtime does not need
to read and hash a game file merely to observe the MVID.

## Exact target guard

The private approved-target record is strict and is never a player-facing
policy. Before classifying a spawn event, all of these must match:

- approved deployment class: `DisposableStagedCopy` or the one exact
  `OwnerDesignatedDisposableLiveInstall` carrying the complete owner-approval
  object;
- canonical root of that approved runtime game target; the owner-designated
  class must equal the recorded installed game root exactly;
- canonical external build-stage root outside the runtime game, save, backup,
  and `Mods` roots;
- canonical approved save-storage root;
- exact `GamePrefs.GameWorld` value;
- exact `GamePrefs.GameName` value;
- exact `World.Guid` when available;
- approved execution type (`LocalSinglePlayer` or `ListenServer` for the first
  probe);
- EAC state `Disabled`; and
- the pinned build fingerprint.

Matching is ordinal and exact. No partial-name, nearest-folder, case-folded,
player-name, platform-ID, or server-address fallback exists. The target record
is private test configuration and must not be copied into public evidence.

The owner-designated class does not broaden probe behavior. It authorizes only
the same observation-only code in one named new disposable game. Existing
saves/worlds, existing Mods and Harmony, core game files, and the project
workspace remain foreign/read-only. Installation may create only the exact
owned DEV Mod folder after payload-specific approval. A wipe, reinstall, or
broad deletion is never implied and requires a separate exact approval.

If the target cannot be established, the handler returns before entity access
and emits only an allowlisted reason code. The probe never repairs or broadens a
record.

## Event decision order

For each callback, the handler follows this order:

1. Confirm the module has not exceeded its log/event limits.
2. Confirm exact build compatibility.
3. Confirm the exact approved disposable target and no-EAC lane.
4. Confirm `ConnectionManager.Instance.IsServer`.
5. Classify `RespawnType` without changing it.
6. Resolve the event entity and confirm it is an `EntityPlayer`.
7. Check the bounded in-memory duplicate gate.
8. Record one sanitized result and return.

Only `NewGame` and, provisionally, `EnterMultiplayer` receive the observation
classification `OBS_ELIGIBLE_NEW_CHARACTER`. `LoadedGame`, `Died`, `Teleport`,
`JoinMultiplayer`, and `Unknown` always receive
`OBS_LIFECYCLE_REJECTED`. Phase 1 does not convert eligibility into an action.

## Duplicate observation contract

The observation key may contain the exact world GUID, entity ID, and lifecycle
enum in process memory. None of those values is written or logged. The set is
bounded to 128 entries for the approved process and target. Once full, new
observations fail closed and only one `OBS_DUPLICATE_CAPACITY` line may be
emitted.

A repeated key produces `OBS_DUPLICATE_SUPPRESSED`. Counters never reset merely
because another callback arrives. Process restart is allowed to clear this
observation-only memory; persistent exactly-once behavior belongs to the later
game-owned CVar proof.

## Sanitized game-log contract

Phase 1 uses only the normal game `Log.Out`, `Log.Warning`, and `Log.Error`
methods. It creates no private log file.

Per process, the probe is limited to 64 entries of at most 256 characters each.
Allowed fields are:

- probe version;
- short build-fingerprint token;
- authority enum;
- local/remote enum;
- lifecycle enum;
- entity-resolved boolean;
- duplicate/suppressed count capped at 128;
- elapsed milliseconds capped at 5,000; and
- one reason code from the allowlist below.

It must not log names, IDs, addresses, coordinates, paths, raw `ClientInfo`, raw
exceptions, stack traces, command lines, or arbitrary object serialization.

Initial reason-code allowlist:

```text
OBS_READY
OBS_BUILD_MISMATCH
OBS_TARGET_MISMATCH
OBS_EAC_NOT_DISABLED
OBS_NOT_SERVER
OBS_LIFECYCLE_REJECTED
OBS_ENTITY_UNRESOLVED
OBS_ELIGIBLE_NEW_CHARACTER
OBS_DUPLICATE_SUPPRESSED
OBS_DUPLICATE_CAPACITY
OBS_LIMIT_REACHED
OBS_INTERNAL_FAILURE
```

Unexpected exceptions are reduced to `OBS_INTERNAL_FAILURE`; raw exception text
is not emitted until a dedicated sanitizer has a passing fixture.

## Phase 1 test sequence

The first approved target is local single-player or a listen server with EAC
disabled. Each case begins from a restorable backup and compares before/after
manifests:

1. incompatible build guard using a pure fixture only;
2. non-allowlisted world and game names;
3. eligible `NewGame` observation;
4. eligible/provisional `EnterMultiplayer` observation when that lane exists;
5. `LoadedGame` after reload;
6. `Died` after ordinary death;
7. `Teleport` classification without the probe causing a teleport;
8. `JoinMultiplayer` after reconnect;
9. duplicate callback suppression; and
10. clean removal followed by an ordinary no-probe launch.

Every runtime case must prove zero probe-caused change to position, CVars,
quests, rewards, XP, gamestage, inventory, health, save content, and owned or
foreign files.

## Phase 1 promotion decision

Phase 1A remains NO-GO unless all of the following are observed:

- exact build and target guards fail closed;
- only the authoritative server path is considered eligible;
- `NewGame` is distinguishable from reload, reconnect, death, and teleport;
- `EnterMultiplayer` is proven to mean a genuinely new server character before
  it is allowed beyond observation;
- duplicate observations are bounded and suppressed;
- normal quests, rewards, XP, progression, and save state are unchanged;
- removal and rollback succeed; and
- logs contain no forbidden data.

Dedicated-server, clean-client, and EAC results may be recorded later, but no
support claim is allowed until each exact lane has direct evidence.
