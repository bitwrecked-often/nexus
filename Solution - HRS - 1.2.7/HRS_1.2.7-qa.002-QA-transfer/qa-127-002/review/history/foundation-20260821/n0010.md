## Design Review — What Is Working Well

### The experience was clarified before implementation

The project began as a deliberately cloudy player-experience idea and was
shaped through sequential, narrow questions before runtime code was written.
That process produced three modes with distinct purposes—Vanilla, Random, and
Wilderness—without pretending that every detail was obvious at the start.

This is valuable because implementation will now be measured against an
expressed experience instead of being allowed to define the product by
accident.

### Vanilla is treated as a protected baseline

Bypassed and Vanilla behavior remain genuine no-op paths. They do not relocate
the player, generate coordinates, add protection, filter spawnpoints, or alter
normal game progression.

This makes comparison testing, user trust, failure handling, and rollback much
stronger. It also prevents custom mechanics from leaking into the ordinary game
experience merely because the helper is installed.

### Discovery used the installed game instead of stale assumptions

The current game assembly, ModAPI surface, Harmony wrapper, EAC behavior,
world/save layout, and spawnpoint files were inspected before implementation.
This established that the preferred route is the native spawn event and native
teleport infrastructure. No Harmony-file modification or initial Harmony patch
is indicated.

That finding reduced risk before code existed and demonstrated the value of
evidence-led discovery.

### The launcher and runtime have separate responsibilities

The launcher owns player or server-owner intent: world selection, policy,
validation, confirmation, local records, and launch. The runtime helper owns one
narrow gameplay responsibility: safely handling an eligible new-character
event under the cached session policy.

This boundary keeps presentation and policy storage outside the game while
keeping player placement server-authoritative.

### Unnecessary product and operational bloat has been rejected

The current design does not add pending policies, hidden installers, telemetry,
private player databases, unrelated support exporters, or a Git-shaped customer
workflow. The Saved Settings Record is local support evidence, not a commit or
publication action.

Each additional mechanism must solve a demonstrated requirement and receive an
explicit capability boundary.

### The interview method improved the design

One yes/no decision at a time has proven appropriate for this project. It gives
the owner room to discover the intended experience while keeping individual
decisions understandable and reviewable.

The method should continue whenever a product ambiguity materially changes the
runtime, persistence, safety, or launcher design.

### Dangerous behavior was identified before implementation

Phase 0 surfaced duplicate spawn events, reconnect and respawn distinctions,
unloaded-chunk behavior, EAC limitations, protection cleanup, save-identity
collisions, client/server agreement, and the irreversibility of a completed
relocation.

Finding these issues now allows them to become test gates and state-machine
requirements rather than customer-facing surprises.

### Rollback claims remain honest

Bypassing or removing the helper restores future vanilla behavior, but it does
not magically return an already relocated character to the original position.
An exact positional rollback requires a save backup or disposable test save.

The project should keep stating this limitation plainly instead of promising a
reversal mechanism that does not exist.

### Framework rigor is being reused without merging projects

The Wasteland project contributes process discipline, UI philosophy, logging,
validation, packaging, and rollback expectations. Historical Random Start - Alpha 6 Method
retains its own identity, module contract, payload, evidence, versions, tests,
and release decision.

This preserves the value of the proven framework without importing animal-
specific behavior or creating the out-of-scope umbrella module.

### The player-facing experience remains simple and playful

The player should see a small, clear set of choices and an honest green or red
status. Green may mean that a fresh character lands somewhere surprising—"la
la land" in the design conversation—but the machinery behind that choice must
remain bounded, deterministic in its safety rules, observable, and fail closed.

That contrast is a strength: the visible product can feel adventurous because
the invisible safety system is deliberately boring and rigorous.

### 2026-08-20 — Phase 1A atomic-semantic relocation breakthrough

- `[Problem history]` The native placement call had already succeeded, but
  comparing a comprehensive player-state digest on later update ticks produced
  `RELOC_SEMANTIC_CHANGED`. Health, stamina, food, water, progression, item,
  and buff state can tick independently between updates, so that interval did
  not isolate the synchronous effect of placement.
- `[Correction]` Keep the full semantic digest, capture it immediately before
  the single player placement, synchronize the existing chunk observer, and
  capture it again in that same deferred `GameUpdate` callback. Require atomic
  equality before starting later read-only chunk, safety, and distance
  verification. Never compare naturally ticking semantic state across later
  updates.
- `[Deterministic artifact]` Two clean builds were byte-identical at SHA-256
  `632208686E0C5A2156DC27B32FD3579F80A0AC9E60171B262E1147AEEE8EFCE2`.
  Compiled-IL review and Defender scans passed before the exact two-file
  payload was staged and recoverably installed.
- `[Menu-name trap]` After the disposable Phase 1A target was reset, the menu
  still exposed the older `HRS_Phase1_Test_001` name without the `A`. A first
  Continue attempt against the absent reset save failed in native
  `XUiC_ContinueGame.startGameCo`; the probe emitted only `RELOC_READY` and no
  world loaded. A later New Game spawn using the old no-`A` name was safely
  rejected with `RELOC_TARGET_REJECTED` and performed no relocation.
- `[Exact target]` The successful run required a genuinely new Navezgane game
  named `HRS_Phase1A_Test_001`. This distinction matters: the no-`A` and
  with-`A` names are different save targets and must never be treated as
  interchangeable.
- `[Breakthrough]` On the exact new target, the probe emitted, in order,
  `RELOC_PLACEMENT_DEFERRED`, `RELOC_PLACEMENT_CALLED`,
  `RELOC_SEMANTIC_UNCHANGED`, and `RELOC_COMPLETED`. The player visibly spawned
  at the relocated position. This is the first clean runtime proof that the
  native-aligned deferred relocation can preserve the reviewed comprehensive
  semantic state across the atomic placement boundary and complete its bounded
  verifier.
- `[Normal exit]` The owner exited normally. The exact completed target persisted
  with 77 files, 20,815,822 bytes, and aggregate
  `8593ABDF5D4256F7C5EEFFB2D2E54C52AD27E2EDCCC88BFB8F13D5F642E2EB67`.
  Game-managed and foreign-mod aggregates exactly matched baseline.
- `[Evidence limitation]` The broad foreign-save aggregate did not match because
  the same client session first opened and saved the older no-`A` target, and
  New Game also updated root save metadata. Timestamp scope after corrected
  launch was confined to the two HRS target directories plus
  `newGameOptions.sdf` and `serveradmin.xml`; nevertheless, the aggregate-only
  baseline cannot prove byte preservation for every unrelated save after that
  mistaken load. Do not report this mixed session as a full protected-save-tree
  pass.
- `[Still pending]` Read-only reload must prove the completed marker persists
  and prevents a second placement. A later cleanly isolated run may be used if
  a strict all-foreign-saves before/after proof is required.
- `[Methods expansion]` The whitepaper-grade scientific reasoning, operational
  hypotheses, causal boundary, layered evidence model, provenance limits,
  threats to validity, and preregistered replication protocol are detailed in
  `n0192.md`.
  The method is classified as an iterative engineering case study with a
  single-case instrumented demonstration, not a statistically powered
  controlled experiment.

  expanded placement, protection, rooftops, and packaging consume the proven
  core later. They do not redefine Standard, exactly-once behavior, or the
  target boundary, and failure of a higher layer does not invalidate a lower
  proven layer.
- `[Evidence]` Completion includes correlated launcher policy, runtime result,
  marker persistence, reload/no-repeat behavior, rollback, and current-truth
  documentation. Evidence is not deferred cleanup.
- `[AI execution]` Once the bounded bridge packet is READY, a higher-level AI
  should resolve ordinary implementation and test failures through retesting
  until the core gate passes. Only genuine human/external, destructive,
  compatibility, privacy/publication, or contradictory-requirement boundaries
  justify a pause.
- `[Whitepaper]` These lessons and their methodological implications are now
  consolidated in Section 15 of
  `n0192.md`.

### 2026-08-21 — Steam launch remains exclusively user-controlled

- `[Owner decision]` The initial frontend must not launch Steam or the game.
  The owner considers AI-driven Steam launch a violation of the user's computer
  boundary.
- `[Frontend boundary]` After saving a validated policy, the launcher displays
  `WAITING_FOR_USER` and plain-language instructions only. It has no Start Game
  button, Steam URI invocation, process start, automation, attachment, sign-in,
  or command channel.
- `[Human demarcation]` The owner independently opens Steam and selects the
  game's normal non-EAC launch option. The AI prepares and later verifies; it
  never claims or attempts to perform the account/process action.
- `[Runtime]` The saved policy remains inert until the independently launched
  game loads the runtime helper and all normal policy, target, lifecycle, and
  marker gates pass.
- `[Future change]` This is a hard core security boundary. Any future proposal
  for user-clicked launch integration requires a new explicit owner decision
  and cannot be inferred from successful core completion.

### 2026-08-21 — EAC is detected and explained, never controlled

- `[Owner decision]` The user must choose the game's normal non-EAC launch lane
  for this managed-code mod. The package may check and report the lane, but it
  must never disable, lower, configure, bypass, patch, stop, or otherwise alter
  anti-cheat.
- `[Pre-launch truth]` Before the owner launches, the frontend can state only
  `Non-EAC required`; it cannot truthfully claim the state is confirmed.
- `[Runtime gate]` Random remains ineligible until a separately reviewed
  read-only runtime signal positively confirms the approved lane. Active,
  unknown, missing, or ambiguous evidence causes no reservation, selection, or
  placement.
- `[Absent-helper case]` If EAC prevents the helper from loading, the helper
  cannot explain its own absence. Missing result therefore means
  `RUNTIME LANE UNCONFIRMED`, not proof that EAC is active or disabled.
- `[Recovery]` The UI tells the owner to exit normally and independently
  relaunch from Steam using the normal non-EAC option. There is no automatic
  fix and no mid-session anti-cheat change.

### 2026-08-21 — Historical Random Start is a solution capsule

- `[Owner framing]` Treat the product like a Docker-style capsule for ownership
  and lifecycle purposes. This is an analogy for isolation and inventory, not
  a claim that the game is containerized.
- `[Ownership]` The capsule owns only its installation-manifest entries:
  Historical Random Start tooling, policy/result records, runtime payload, and
  recovery metadata. Proximity and similar naming never establish ownership.
- `[Host boundary]` The base game, Steam, saves/worlds, shared Harmony/runtime
  layers, other mods, shared Bit Wrecked tooling, and other solutions remain
  external. This capsule may verify declared dependencies read-only but never
  install, repair, modify, disable, or remove them.
- `[State metric]` The upper interface shows one plain-language state; technical
  inventory, hashes, dependency observations, and uninstall live behind one
  Details disclosure in keeping with the accepted minimalist guidance.
- `[Launch independence]` Launch Game remains available regardless of capsule
  configuration. Incomplete configuration produces `Configuration incomplete —
  mod not enabled` and ordinary game behavior.
- `[Uninstall]` The Historical Random Start uninstall action is always
  available and independently confirmed. It removes only validated
  manifest-owned capsule artifacts and verifies each is absent.
- `[Truth]` Success says `Historical Random Start removed`. It does not say all
  Bit Wrecked material is removed, the entire host is vanilla, or historical
  gameplay effects were reversed.
- `[Drift]` Unknown or changed artifacts are preserved and reported. An
  uninstall problem can never justify widening deletion beyond the capsule.

### 2026-08-21 — Harmony and other-mod coexistence remains bounded

- `[Evidence]` The successful Phase 1A run used native game/ModAPI behavior,
  did not patch or modify Harmony, and preserved the measured game-managed and
  foreign-mod aggregates in that exact pinned run.
- `[Claim limit]` One successful atomic run does not establish universal
  compatibility with every mod, load order, game build, or shared runtime.
- `[Isolation]` Historical Random Start owns a unique capsule Mod folder,
  ModInfo identity, assembly identity, and policy/result identities. Harmony,
  shared runtimes, and unrelated mods remain external and read-only.
- `[Preflight]` Install/update checks only the bounded collision surface:
  recognized capsule version, owned-file inventory/drift, unique identities,
  game/API lane, declared shared-runtime compatibility, and known static
  first-spawn/relocation collisions.
- `[No broad scan]` The capsule does not recursively classify or hash every
  unrelated mod to manufacture a compatibility claim. Unknown neighboring mods
  remain unproven, not automatically incompatible.
- `[Conflict result]` Unknown files in the owned destination, unapproved owned
  drift, or an identity collision produces `Existing installation requires
  review` before overwrite. Launch remains available, this mod remains
  inactive, and no neighboring artifact is changed.
- `[Runtime evidence]` Later integration tests must watch for duplicate spawn
  callbacks, competing movement, unexpected final position, and aggregate
  drift before any broader coexistence claim.

### 2026-08-21 — Alpha UX interview supersedes the earlier no-launch decision

- `[Supersession]` The earlier entry forbidding a Start Game control remains as
  decision history but is no longer current. The owner later authorized one
  always-visible `Launch Game` button with a stricter activation boundary.
- `[User demarcation]` Only the local person who opened the manager may activate
  Launch Game. Steam must be running. AI, timers, recovery, default focus,
  synthetic input, and automatic continuations cannot activate it.
- `[Incomplete configuration]` Launch remains available, while the upper status
  area says `Configuration incomplete — mod not enabled`. The button itself
  stays visually and verbally clean.
- `[Mutation lock]` When any game client/server instance is running, every
  capsule-changing action is unavailable. Read-only viewing may continue. No
  change is queued. Steam activity alone is not the mutation lock.
- `[Recovery evidence]` Every attempt enters local history and shares a
  correlation ID with its user note and diagnostic log. Default plus the five
  latest attempts remain visible; failed or stale entries stay in the list but
  cannot restore. A known-good entry must revalidate immediately before use.
- `[Removal vocabulary]` `Remove from Game` supersedes uninstall language. It
  removes only validated solution artifacts deployed into game paths. The
  portable manager, notes, history, and evidence remain, and Windows system
  files are never install/removal targets.
- `[Explanation model]` Adopt sound clarity, hierarchy, progressive-disclosure,
  and accessibility guidance as reasoning inputs, not a visual style to copy.
  Essential state remains visible; tooltips briefly explain control outcomes
  and have equivalent accessible descriptions.
- `[Process lesson]` The manifest is durable project memory. A frontier agent
  can execute engineering work persistently because authority, completion,
  recovery, and human-only boundaries are explicit rather than remembered from
  chat context.
